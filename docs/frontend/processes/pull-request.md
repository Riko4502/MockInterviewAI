# Pull Request Policy

---

## 1. Чек-лист перед созданием PR

Перед отправкой изменений на ревью убедитесь, что:
- [ ] Все тесты проходят локально (`pnpm test`).
- [ ] Линтер не выдает ошибок (`pnpm --filter web lint`).
- [ ] Проверка типов успешна (`pnpm typecheck`).
- [ ] Проект успешно собирается (`pnpm build`).
- [ ] Созданы Storybook stories для новых UI-компонентов.

---

## 2. Требования к оформлению PR

1. **Заголовок:** в формате Conventional Commits.
2. **Описание:**
   - Что было сделано и почему.
   - Ссылка на задачу в трекере.
   - Скриншоты или анимации для визуальных изменений в UI.

### Разрешённые типы коммитов

| Тип       | Когда использовать                              |
|-----------|------------------------------------------------|
| `feat`    | Новая функциональность                         |
| `fix`     | Исправление бага                               |
| `refactor`| Переработка кода без изменения логики          |
| `perf`    | Улучшение производительности                   |
| `docs`    | Изменения в документации                       |
| `test`    | Добавление или исправление тестов              |
| `style`   | Форматирование, опечатки, правки стиля кода    |
| `chore`   | Обслуживание проекта (зависимости, тулинг, CI) |
| `ci`      | Изменения в CI/CD конфигурации                 |

### Формат сообщения

```
тип(scope): сообщение
```

- `scope` — обязателен, указывает контекст изменений (например, `web`, `ui`, `api`, `docs`).
- Сообщение — на русском или английском, без точки в конце (не настроено в валидаторе, но принято по код-стайлу проекта).

---

## 3. Правила ревью и слияния

* PR должен получить необходимые **Approve** от коллег.
* Все комментарии и замечания с `Request Changes` должны быть устранены.
* Слияние выполняется методом **Squash and merge** или согласно принятой в проекте стратегии.
