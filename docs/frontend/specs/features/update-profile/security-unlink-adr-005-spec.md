# Спецификация: безопасная отвязка аккаунтов по ADR-005 (features/update-profile)

## 1. Цель

Сформулировать требования к фронтенду для реализации безопасной отвязки привязанных аккаунтов (Telegram, GitHub) после появления backend-флоу по [ADR-005](../../../../../docs/adr/ADR-005.md).

Ключевые требования ADR-005, которые необходимо отразить на фронте:

- Подтверждение отвязки Telegram **одноразовым кодом из Telegram** (одноразовый токен с TTL).
- Обеспечение **ревокации сессий** при отвязке (инкремент `generation`).
- Использование **корректных эндпоинтов отвязки** (не через `PATCH /profile/me` с `telegramUsername: null` / `gitUrl: null`).
- Предупреждающий диалог перед выполнением отвязки с ясным текстом о последствиях.

## 3. Обоснование

Текущая реализация веб-отвязки использует `PATCH /profile/me` с установкой `telegramUsername: null` / `gitUrl: null` (см. `ConnectedAccountsSection.tsx`, обработчики `handleUnlinkTelegram`/`handleUnlinkGithub`).

Согласно ADR-005:

- Backend-флоу подтверждаемой отвязки Telegram требует **одноразового кода из Telegram** и отдельного user-facing эндпоинта. Непосредственное обнуление через `PATCH /profile/me` не соответствует целевому флоу безопасности.
- При отвязке привязок (Telegram/GitHub) должна выполняться **ревокация сессий** (инкремент `generation`), что влияет на все остальные активные сессии пользователя.
- Эндпоинты отвязки в `@packages/api` (Orval/OpenAPI) должны использоваться явно (не смешивать с общей мутацией обновления профиля для операции отвязки).

На текущем этапе (до появления backend-реализации ADR-005) подключение диалогов с текстом о принудительном завершении сессий было бы **ложной гарантией безопасности**. Данная спецификация описывает целевое состояние **после** появления соответствующего backend-флоу.

## 4. Предположения и ограничения

- **Статус реализации ADR-005 — «Не реализовано» на backend** (см. ADR-005 §«Статус реализации»). Данная спецификация описывает фронтовую часть, которая активируется/реализуется после появления backend-эндпоинтов.
- Общий `ConfirmDialog` в `@packages/ui` уже существует, переиспользуется.
- Подтверждение отвязки Telegram кодом из Telegram — UI-флоу (запрос одноразового токена, ввод/подтверждение кода, ожидание ответа). Детали эндпоинтов уточняются по OpenAPI после backend-работ (см. ADR-005).
- При отвязке GitHub также должна выполняться ревокация сессий (инкремент `generation`) согласно ADR-005 (отвязка GitHub входит в объём задачи).
- Тексты предупреждений не должны давать ложных гарантий — они должны точно отражать поведение (принудительное завершение остальных активных сессий).

## 5. Требования

### 5.1. Функциональные требования

1. **Подтверждение отвязки через диалог.** При клике «Отвязать Telegram» или «Отвязать GitHub» **не** вызывать мутацию немедленно. Сначала открывать подтверждающий диалог `ConfirmDialog` (из `@packages/ui`).
2. **Текст предупреждения (безопасность).** В диалоге отображать предупреждение о том, что при отвязке аккаунта **все остальные активные сессии на других устройствах будут принудительно завершены** в целях безопасности (в соответствии с ревокацией через инкремент `generation` по ADR-005).
3. **Отвязка Telegram — подтверждение кодом (целевой флоу).** Реализовать UI-флоу подтверждения отвязки Telegram одноразовым кодом из Telegram (по одноразовому токену с TTL), как описано в ADR-005. UI должен поддерживать:
- Запрос генерации одноразового токена для отвязки Telegram (если предусмотрено backend-эндпоинтом).
- Отображение инструкций/кода (или ожидания кода в Telegram) в соответствии с контрактом API.
- Подтверждение кода и выполнение отвязки по корректному эндпоинту.
- Обработку ошибок (истёк TTL, неверный код, уже отвязан и др.).
4. **Использование корректных эндпоинтов отвязки.** Для операций отвязки использовать **специальные эндпоинты отвязки** из `@packages/api` (сгенерированные по OpenAPI), а не `PATCH /profile/me` с обнулением полей. При отсутствии сгенерированных мутаций — добавить использование корректных методов после регенерации API.
5. **Ревокация сессий (generation).** Обеспечить, чтобы после успешной отвязки (Telegram/GitHub) применялась логика ревокации сессий (инкремент `generation`) — поведение должно соответствовать backend-ответу/контракту. На фронте не инкрементируем generation вручную, только правильно вызываем эндпоинт и обрабатываем ответ.
6. **Обработка состояний.** Во время выполнения мутаций блокировать закрытие диалога, дизейблить кнопки (использовать `isPending`/внутреннее `isBusy`), отображать спиннер в кнопке подтверждения.
7. **Успех/ошибка.** По успешной отвязке — показывать тост успеха (`profile.telegramUnlinkSuccess` / `profile.githubUnlinkSuccess`), инвалидировать кэш профиля (`getProfileControllerGetMyProfileQueryKey()`), закрывать диалог. При ошибке — показывать тост ошибки, диалог **не** закрывать (оставить открытым для повтора).
8. **GitHub отвязка.** Аналогично Telegram — подтверждение через диалог с предупреждением о ревокации сессий. При целевом флоу ADR-005 GitHub-отвязка также должна использовать отдельный эндпоинт с ревокацией сессий (см. ADR-005 «Объём по отвязке GitHub»).

### 5.2. Нефункциональные требования

- **Соответствие FSD.** Изменения только в `features/update-profile` (UI + при необходимости модель). Не выносить логику за пределы фичи без необходимости.
- **Переиспользование.** Использовать существующий `ConfirmDialog` из `@packages/ui` (без дублирования).
- **Типобезопасность.** Все вызовы API типизировать через `@packages/api`. Не использовать `any`.
- **i18n.** Все пользовательские тексты — через `react-i18next`, ключи в `common.json` (ru/en). Не хардкодить строки.
- **UX.** Диалог нельзя закрыть во время выполнения запроса (Esc/оверлей/крестик заблокированы, когда `isBusy`).
- **Безопасность.** Не раскрывать чувствительные данные в UI (коды — только в рамках предусмотренного флоу). Тексты предупреждений корректные, без ложных гарантий.

## 6. Зависимости

### 6.1. Зависимости (внешние по задаче)

- Backend: реализация эндпоинтов отвязки по ADR-005 (user-facing эндпоинты для отвязки Telegram/GitHub), генерация OpenAPI → Orval → `@packages/api`.
- При отсутствии сгенерированных хуков в `@packages/api` — дождаться регенерации перед подключением UI.

### 6.2. Внутренние зависимости

- `@packages/ui` — `ConfirmDialog` (уже есть).
- `@packages/api` — хуки мутаций отвязки (после регенерации), типы `UserProfileDto`.
- `@packages/i18n` — ключи переводов.
- `apps/web/src/features/update-profile/ui/ConnectedAccountsSection.tsx` — основной файл правки.
- `apps/web/src/features/update-profile/model/*` — при необходимости.

## 7. Критерии приёмки (Definition of Done)

### DoD (обязательные)

- [ ] `ConnectedAccountsSection.tsx` подключает `ConfirmDialog` для отвязки Telegram и GitHub (клики не вызывают мутацию напрямую).
- [ ] Реализован UI-флоу подтверждения отвязки Telegram одноразовым кодом из Telegram (в соответствии с контрактом API после его появления). При отсутствии финального контракта на момент реализации — заложить расширяемую структуру состояния (state machine) без потери типобезопасности.
- [ ] Для отвязки используются **корректные эндпоинты** из `@packages/api` (не `PATCH /profile/me` с `null`). Мутации обновления профиля не используются для самой операции отвязки там, где есть специализированные эндпоинты.
- [ ] Предупреждающий текст диалога корректно отражает ревокацию остальных активных сессий (инкремент `generation`).
- [ ] По успеху — тост, инвалидируем кэш профиля, диалог закрывается. По ошибке — тост, диалог остаётся открытым.
- [ ] Во время выполнения — кнопки/закрытие заблокированы, отображается спиннер.
- [ ] Добавлены/обновлены ключи i18n (ru/en) для всех новых текстов (диалог, инструкции по коду Telegram, статусы).
- [ ] Покрыты unit-тестами ключевые сценарии (открытие диалога, отмена не вызывает мутацию, подтверждение вызывает корректную мутацию отвязки, блокировка во время pending, обработка ошибки).
- [ ] `pnpm --filter web exec tsc --noEmit` — без ошибок.
- [ ] `pnpm --filter web exec vitest run` — успешно (включая новые тесты).
- [ ] Соответствие правилам монорепо, FSD, стилю кода проекта.

### Дополнительные проверки (из шаблона)

- [ ] Нет хардкода строк в новых/изменённых компонентах (только i18n).
- [ ] Типы берутся из `@packages/api`/`@packages/dto`, локальных дублирующих типов нет.

## 9. Риски

- **Зависимость от backend**: финальный контракт эндпоинтов/флоу Telegram-кода может отличаться. Рекомендуется заложить абстракцию (интерфейс хука) и расширяемое состояние UI, чтобы минимизировать правки при интеграции.
- **Ложное восприятие гарантий**: текст предупреждения должен точно соответствовать тому, что делает backend (ревокация сессий через `generation`). Не упоминать то, чего нет.
- **Регрессии существующего UX привязки**: не ломать диалог привязки Telegram через виджет (Telegram Login Widget) — изменения только в блоке отвязки.
- **Race conditions**: при быстром повторном клике — блокировать кнопки, использовать `isPending`.
