# Спецификация: безопасная отвязка аккаунтов по ADR-005 (features/update-profile)

## 1. Цель

Сформулировать требования к фронтенду для реализации безопасной отвязки привязанных аккаунтов (Telegram, GitHub) после появления backend-флоу по [ADR-005](../../../../../docs/adr/ADR-005.md).

**Роль документа:** это «зонтичная» спека — общие требования, зависимости и DoD. Детальный UI-флоу (шаги, состояния, тексты, тест-кейсы) вынесен в [security-unlink-frontend-spec.md](./security-unlink-frontend-spec.md); порядок работ — в [security-unlink-adr-005-plan.md](./security-unlink-adr-005-plan.md). Backend-часть — в `docs/backend/specs/` (см. §2).

Ключевые требования ADR-005, которые необходимо отразить на фронте:

- Подтверждение отвязки Telegram **одноразовым кодом из Telegram** (единственный секрет — код с TTL, см. D5).
- Обеспечение **ревокации сессий** при отвязке (инкремент `generation`).
- Использование **корректных эндпоинтов отвязки** (не через `PATCH /profile/me` с `telegramUsername: null` / `gitUrl: null`).
- Предупреждающий диалог перед выполнением отвязки с ясным текстом о последствиях.

## 3. Обоснование

Текущая реализация веб-отвязки использует `PATCH /profile/me` с установкой `telegramUsername: null` / `gitUrl: null` (см. `ConnectedAccountsSection.tsx`, обработчики `handleUnlinkTelegram`/`handleUnlinkGithub`).

Согласно ADR-005:

- Backend-флоу подтверждаемой отвязки Telegram требует **одноразового кода из Telegram** и отдельного user-facing эндпоинта. Непосредственное обнуление через `PATCH /profile/me` не соответствует целевому флоу безопасности.
- При отвязке привязок (Telegram/GitHub) должна выполняться **ревокация сессий** (инкремент `generation`), что влияет на все сессии пользователя, включая текущую.
- Эндпоинты отвязки в `@packages/api` (Orval/OpenAPI) должны использоваться явно (не смешивать с общей мутацией обновления профиля для операции отвязки).

На текущем этапе (до появления backend-реализации ADR-005) подключение диалогов с текстом о принудительном завершении сессий было бы **ложной гарантией безопасности**. Данная спецификация описывает целевое состояние **после** появления соответствующего backend-флоу.

## 3.1. Принятые решения (фронт, 2026-10-17)

Контракт backend зафиксирован в [backend-спеке, §1.1](../../../../backend/specs/security-unlink-adr-005-spec.md) (D1–D14). Фронтовые следствия:

- **F1 (из D2).** `PATCH /profile/me` больше **не отвязывает** — обнуление `telegramUsername`/`gitUrl` отклоняется сервером. Ветка отвязки через `updateProfileMutation` из UI удаляется полностью (без fallback), тесты переписываются на новые эндпоинты.
- **F2 (из D4).** Эндпоинты: `POST /profile/me/telegram/unlink/request`, `POST /profile/me/telegram/unlink/confirm`, `POST /profile/me/github/unlink`. Хуки Orval появятся после регенерации `@packages/api`.
- **F3 (из D5).** `confirm` принимает **только** `{ code }` — отдельного токена в теле нет. Шаг ввода кода доступен после `request`; `request` возвращает `expiresAt` для обратного отсчёта; «Отправить код ещё раз» с cooldown.
- **F4 (из D7/D8).** Отвязка Telegram инкрементирует `generation` и отзывает **текущую** сессию тоже. Поэтому после успеха — логаут по паттерну `ChangePasswordSection` (тост + `router.replace(paths.login)`), а текст предупреждения говорит «все сессии, включая текущую».
- **F5.** Привязка Telegram на `dev` переведена на deep-link token flow, виджет (Telegram Login Widget) удалён. Ссылки на `linkTelegramMutation`/виджет неактуальны; привязка сама становится security-событием (D3) и тоже отзывает остальные сессии.
- **F6.** Для кнопки отмены использовать существующий ключ `actions.cancel` (не `profile.cancel` с `defaultValue`).
- **F7. Маппинг ошибок на i18n:** `INVALID_CODE` → `profile.telegramUnlinkErrorInvalidCode`; `CODE_EXPIRED` → `profile.telegramUnlinkErrorExpired`; `ATTEMPTS_EXCEEDED` → `profile.telegramUnlinkErrorAttempts`; `ALREADY_UNLINKED` → `profile.telegramUnlinkErrorAlreadyUnlinked`; `TELEGRAM_NOT_LINKED`/`GITHUB_NOT_LINKED`/`TOO_MANY_REQUESTS` → generic/rate-limited; `LAST_AUTH_METHOD` → `profile.githubUnlinkErrorLastMethod`.

## 4. Предположения и ограничения

- **Статус реализации ADR-005 — «Не реализовано» на backend** (см. ADR-005 §«Статус реализации»). Данная спецификация описывает фронтовую часть, которая активируется/реализуется после появления backend-эндпоинтов.
- Общий `ConfirmDialog` в `@packages/ui` уже существует, переиспользуется.
- Контракт отвязки зафиксирован (§3.1): один секрет — код, `{ code }` в теле; конкретика путей/статусов — в backend-спеке §1.1.
- При отвязке GitHub также должна выполняться ревокация сессий (инкремент `generation`) согласно ADR-005 (отвязка GitHub входит в объём задачи).
- Тексты предупреждений не должны давать ложных гарантий — они должны точно отражать поведение (принудительное завершение всех сессий, включая текущую).

## 5. Требования

### 5.1. Функциональные требования

1. **Подтверждение отвязки через диалог.** При клике «Отвязать Telegram» или «Отвязать GitHub» **не** вызывать мутацию немедленно. Сначала открывать подтверждающий диалог `ConfirmDialog` (из `@packages/ui`).
2. **Текст предупреждения (безопасность).** В диалоге отображать предупреждение о том, что при отвязке аккаунта **все сессии, включая текущую, будут принудительно завершены** в целях безопасности (в соответствии с ревокацией через инкремент `generation` по ADR-005), после чего потребуется повторный вход.
3. **Отвязка Telegram — подтверждение кодом (целевой флоу).** Реализовать UI-флоу подтверждения отвязки Telegram одноразовым кодом из Telegram, как описано в ADR-005. UI должен поддерживать:
- Запрос одноразового кода (`POST /profile/me/telegram/unlink/request`) — код отправляет бот в Telegram.
- Шаг ввода кода с инструкцией, обратным отсчётом по `expiresAt` и кнопкой «Отправить код ещё раз» (с cooldown).
- Подтверждение: `POST /profile/me/telegram/unlink/confirm` с телом **только** `{ code }` (F3).
- Обработку ошибок по маппингу F7 и успешный логаут (F4).
4. **Использование корректных эндпоинтов отвязки.** Для операций отвязки использовать **специальные эндпоинты отвязки** из `@packages/api` (сгенерированные по OpenAPI), а не `PATCH /profile/me` с обнулением полей. При отсутствии сгенерированных мутаций — добавить использование корректных методов после регенерации API.
5. **Ревокация сессий (generation).** Обеспечить, чтобы после успешной отвязки (Telegram/GitHub) применялась логика ревокации сессий (инкремент `generation`) — поведение должно соответствовать backend-ответу/контракту. На фронте не инкрементируем generation вручную, только правильно вызываем эндпоинт и обрабатываем ответ.
6. **Обработка состояний.** Во время выполнения мутаций блокировать закрытие диалога, дизейблить кнопки (использовать `isPending`/внутреннее `isBusy`), отображать спиннер в кнопке подтверждения.
7. **Успех/ошибка.** По успешной отвязке — показывать тост успеха (`profile.telegramUnlinkSuccess` / `profile.githubUnlinkSuccess`), инвалидировать кэш профиля (`getProfileControllerGetMyProfileQueryKey()`), закрывать диалог. При ошибке — показывать тост ошибки, диалог **не** закрывать (оставить открытым для повтора).
8. **GitHub отвязка.** Аналогично Telegram — подтверждение через диалог с предупреждением о ревокации сессий. При целевом флоу ADR-005 GitHub-отвязка также должна использовать отдельный эндпоинт с ревокацией сессий (см. ADR-005 «Объём по отвязке GitHub»). Отвязка последнего способа входа отклоняется сервером (`409 LAST_AUTH_METHOD`, D9) — сообщение показывается пользователю.
9. **Логаут после успеха (F4).** Отвязка отзывает и текущую сессию, поэтому по успеху — тост и переход на `paths.login` (паттерн `ChangePasswordSection.tsx`), а не возврат на живой профиль. Кэш профиля инвалидируется до перехода.

### 5.2. Нефункциональные требования

- **Соответствие FSD.** Изменения только в `features/update-profile` (UI + при необходимости модель). Не выносить логику за пределы фичи без необходимости.
- **Переиспользование.** Использовать существующий `ConfirmDialog` из `@packages/ui` (без дублирования).
- **Типобезопасность.** Все вызовы API типизировать через `@packages/api`. Не использовать `any`.
- **i18n.** Все пользовательские тексты — через `react-i18next`, ключи в `common.json` (ru/en). Не хардкодить строки.
- **UX.** Диалог нельзя закрыть во время выполнения запроса (Esc/оверлей/крестик заблокированы, когда `isBusy`).
- **Безопасность.** Не раскрывать чувствительные данные в UI (коды — только в рамках предусмотренного флоу). Тексты предупреждений корректные, без ложных гарантий.

## 9. Риски

- **Зависимость от backend**: контракт зафиксирован (backend-спека §1.1); до регенерации `@packages/api` заложить абстракцию (интерфейс хука), чтобы минимизировать правки при интеграции.
- **Ложное восприятие гарантий**: текст предупреждения должен точно соответствовать тому, что делает backend (ревокация сессий через `generation`, включая текущую). Не упоминать то, чего нет.
- **Регрессии существующего UX привязки**: виджет Telegram удалён (dev, deep-link token flow) — не восстанавливать его и не ориентироваться на `linkTelegramMutation`; привязка должна продолжать работать после изменений в блоке отвязки.
- **Race conditions**: при быстром повторном клике — блокировать кнопки, использовать `isPending`; на `request` действует серверный rate limit 1/60с (D5) — обрабатывать `429`.
