# Спецификация: безопасная отвязка аккаунтов (frontend) — UI-флоу подтверждения (features/update-profile)

## 1. Цель

Сформулировать требования к фронтенду для реализации безопасной отвязки привязанных аккаунтов (Telegram, GitHub) с использованием новых backend-эндпоинтов по [ADR-005](../../../../../docs/adr/ADR-005.md).

**Роль документа:** детализация UI-флоу к «зонтичной» [спецификации security-unlink-adr-005-spec.md](./security-unlink-adr-005-spec.md); общие требования/DoD — там, порядок работ — в [плане](./security-unlink-adr-005-plan.md).

Фокус на UI: `ConfirmDialog`, предупреждения при отвязке Telegram/GitHub, UI-флоу подтверждения одноразового кода из Telegram (запрос кода/ввод кода/подтверждение), переход на новые эндпоинты из `@packages/api`, i18n, тесты.

## 3. Обоснование

Согласно ADR-005, отвязка должна выполняться через специальные эндпоинты с ревокацией сессий (инкремент `generation`) и для Telegram — с подтверждением одноразовым кодом из Telegram. Текущая реализация использует `PATCH /profile/me` с обнулением полей, что некорректно для целевого безопасного флоу.

UI должен:
- Предупреждать пользователя о последствиях (принудительное завершение всех сессий, включая текущую).
- Реализовывать двухшаговый флоу для Telegram (подтверждение намерения → ввод кода из Telegram → подтверждение).
- Использовать новые эндпоинты из `@packages/api` после их регенерации по OpenAPI.
- Корректно обрабатывать состояния загрузки/ошибок.

### 3.1. Принятые решения (фронт)

Контракт и решения — [backend-спека, §1.1](../../../../backend/specs/security-unlink-adr-005-spec.md); фронтовые следствия — [«зонтичная» спека, §3.1](./security-unlink-adr-005-spec.md#31-принятые-решения-фронт-2026-10-17) (F1–F7). Кратко для этого UI-флоу:

- `confirm` принимает **только** `{ code }` (без токена).
- Ветка отвязки через `updateProfileMutation`/`PATCH /profile/me` удаляется — только новые эндпоинты.
- По успеху — логаут (тост + `router.replace(paths.login)`), т.к. `generation` отзывает и текущую сессию.
- Кнопка отмены — `actions.cancel`; ошибки маппятся на отдельные ключи (F7).
- Привязка Telegram — deep-link token flow (виджет удалён), ссылки на виджет неактуальны.

## 4. Требования

### 4.1. Функциональные требования

1. **ConfirmDialog для подтверждения намерения**
- При клике «Отвязать Telegram» или «Отвязать GitHub» **не** вызывать мутацию сразу. Открывать `ConfirmDialog` из `@packages/ui`.
- Диалог содержит заголовок, описание с предупреждением о ревокации сессий, кнопки «Отмена» и «Подтвердить отвязку» (destructive).
- Во время выполнения запроса диалог нельзя закрыть (блокировать Esc/оверлей/крестик), кнопки дизейблены с отображением спиннера.

2. **Предупреждения при отвязке**
- Для Telegram и GitHub в описании диалога явно указывать: при отвязке **все сессии, включая текущую, будут завершены** (на других устройствах — принудительно) в целях безопасности (ревокация через инкремент `generation`), после чего потребуется повторный вход.
- Тексты предупреждений точные, без ложных гарантий.

3. **UI-флоу подтверждения одноразового кода из Telegram**
Реализовать многошаговый флоу:
- **Шаг 1 (подтверждение намерения)**: ConfirmDialog с предупреждением. При подтверждении — запросить одноразовый код (`POST /profile/me/telegram/unlink/request`).
- **Шаг 2 (ввод кода)**: Показать диалог/форму с инструкцией «Введите одноразовый код, отправленный в Telegram», полем ввода кода, кнопками «Подтвердить» и «Отменить». Доступна кнопка «Отправить код повторно» (с cooldown) и обратный отсчёт по `expiresAt`.
- **Подтверждение**: Отправить **только** `{ code }` на `POST /profile/me/telegram/unlink/confirm`.
- **Обработка ошибок**: неверный код, истёк TTL, аккаунт уже отвязан, превышен лимит попыток, rate limit — показывать понятные сообщения (через i18n, маппинг F7), не закрывать диалог шага ввода кода при ошибке.
- **Успех**: после успешного подтверждения — закрыть все диалоги, показать тост успеха, инвалидировать кэш профиля и выполнить логаут с переходом на `paths.login` (F4).

4. **GitHub отвязка (упрощённый флоу)**
- Подтверждение через `ConfirmDialog` с предупреждением о завершении всех сессий.
- При подтверждении — вызывать `POST /profile/me/github/unlink` из `@packages/api`.
- Успех/ошибка как для Telegram, но без шага ввода кода; по успеху — логаут (F4).
- Отвязка последнего способа входа отклоняется (`409 LAST_AUTH_METHOD`) — показать сообщение, диалог не закрывать.

5. **Переход на новые эндпоинты из `@packages/api`**
- Использовать хуки мутаций, сгенерированные Orval по новому OpenAPI (эндпоинты отвязки Telegram/GitHub).
- Ветку отвязки через `PATCH /profile/me` (`telegramUsername: null` / `gitUrl: null`) **удалить**: сервер её больше не принимает (F1).
- При отсутствии сгенерированных хуков на момент реализации — заложить абстракцию (интерфейс) для минимизации правок при интеграции.

6. **Состояния и UX**
- Состояния: `idle`, `requestingCode`, `awaitingCode`, `submittingCode`, `unlinkingGithub`, `success`, `error` (расширяемые).
- Блокировать повторные клики во время `pending`.
- После ошибки на шаге ввода кода — позволить повторно запросить код или исправить код.
- Сброс состояния при закрытии диалогов (по отмене/успеху).

### 4.2. Нефункциональные требования

- **Соответствие FSD**: изменения в `features/update-profile` (UI + при необходимости `model/`).
- **Переиспользование**: `ConfirmDialog` из `@packages/ui` без дублирования.
- **Типобезопасность**: все вызовы API через `@packages/api`, без `any`.
- **i18n**: все тексты через `react-i18next`, ключи в `packages/i18n/src/locales/{ru,en}/common.json`.
- **UX**: диалоги не закрываются во время выполнения запроса.
- **Безопасность UI**: не отображать/не логировать одноразовые коды, токены. Поле ввода кода — обычное текстовое поле с валидацией.
- **Тестируемость**: компоненты легко тестируются, состояния вынесены при необходимости в хук.

## 8. Риски

- **Зависимость от backend-контракта**: контракт зафиксирован ([backend-спека, §1.1](../../../../backend/specs/security-unlink-adr-005-spec.md)); до регенерации `@packages/api` заложить абстракцию хука, чтобы минимизировать правки.
- **Ложные гарантии**: текст предупреждения должен точно отражать ревокацию через `generation`, включая текущую сессию.
- **Регрессии**: актуальная привязка Telegram — deep-link token flow (виджет удалён на `dev`); не ориентироваться на `linkTelegramMutation`.
- **Race conditions**: блокировать кнопки при `pending`; на `request` действует серверный rate limit 1/60с (D5) — обрабатывать `429`.
