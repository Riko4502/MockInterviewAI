# Регламент Pull Request и Commit Guidelines (Общий для всего проекта)

Данный документ описывает единые правила оформления коммитов, создания и ревью Pull Request (PR) для всех частей монорепозитория: **Frontend** (`web`, `landing`), **Backend** (`api`), **Realtime** (`realtime`), **Code Runner** (`code-runner`), **DevOps/Инфраструктура** и **Packages** (`ui`, `dto`, `types` и др.).

---

## 1. Формат коммитов (Conventional Commits)

В проекте настроен **commitlint** с валидацией через Git-хук **Husky**. Любой коммит должен строго соответствовать формату:

```text
тип(scope): сообщение
```

> ⚠️ **Важно:**
> - `scope` — **обязателен** (правило `"scope-empty": [2, "never"]` в `commitlint.config.mjs`).
> - Сообщение — пишется на русском или английском языке, **без точки в конце** (согласно код-стайлу проекта).

---

### Разрешённые типы коммитов

| Тип | Когда использовать | Пример |
| :--- | :--- | :--- |
| `feat` | Новая функциональность | `feat(web): добавить форму входа с валидацией` |
| `fix` | Исправление бага | `fix(ui): исправить отображение иконки в Input` |
| `refactor` | Переработка кода без изменения логики | `refactor(api): вынести сервис генерации отчетов` |
| `perf` | Улучшение производительности | `perf(realtime): оптимизировать хранение сессий в Redis` |
| `docs` | Изменения в документации | `docs(repo): обновить регламент создания PR` |
| `test` | Добавление или исправление тестов | `test(api): добавить e2e тесты для модуля авторизации` |
| `style` | Форматирование, опечатки, правки стиля кода | `style(landing): исправить отступы в блоке преимуществ` |
| `chore` | Обслуживание проекта (зависимости, тулинг) | `chore(repo): обновить версию pnpm и turbo` |
| `ci` | Изменения в CI/CD конфигурации | `ci(github): добавить шаг проверки типов в pipeline` |

---

### Рекомендуемые области (`scope`)

Область указывает, какую именно часть монорепозитория затрагивают изменения:

* **Приложения (`apps`):**
  * `web` — клиентское веб-приложение (Next.js)
  * `landing` — маркетинговый лендинг (Next.js)
  * `api` — основной бэкенд REST API (NestJS)
  * `realtime` — WebSocket сервис (Go)
  * `code-runner` — сервис запуска кода в песочнице
  * `ui-docs` — документация компонентов (Storybook)
* **Пакеты (`packages`):**
  * `ui` — UI-кит и дизайн-система (`@packages/ui`)
  * `icons` — библиотека иконок (`@packages/icons`)
  * `dto` — структуры передачи данных (`@packages/dto`)
  * `types` — общие TypeScript типы (`@packages/types`)
  * `utils` — общие утилиты (`@packages/utils`)
  * `i18n` — локализация (`@packages/i18n`)
* **Инфраструктура и общее:**
  * `ci` / `devops` — пайплайны GitHub Actions, Docker, Docker Compose
  * `docs` — документация проекта
  * `repo` — конфигурация монорепозитория, husky, biome, turbo

## 2. Чек-лист перед созданием PR

Перед созданием Pull Request убедитесь, что локально выполнены следующие шаги:

```bash
# 1. Проверка линтером и автоформатирование
pnpm lint

# 2. Проверка типов во всех пакетах
pnpm typecheck # или pnpm build

# 3. Запуск тестов
pnpm test
```

- [ ] Все тесты проходят локально (`pnpm test`).
- [ ] Линтер не выдает ошибок (`pnpm lint` или `pnpm lint:fix`).
- [ ] Проверка типов успешна во всех затронутых пакетах.
- [ ] Проект успешно собирается (`pnpm build`).
- [ ] Созданы/обновлены Storybook stories (при изменении UI-компонентов).
- [ ] Созданы/обновлены миграции базы данных (при изменении схемы БД в `api`).

---

## 3. Требования к оформлению Pull Request

1. **Заголовок PR:** формируется по стандарту Conventional Commits (аналогично коммитам, например `feat(web): MOC-12 форма авторизации`).
2. **Описание PR:**
   - **Что сделано:** краткое перечисление изменений.
   - **Зачем:** контекст или ссылка на задачу в таск-трекере (`#MOC-XX`).
   - **Как проверить:** шаги для тестирования проверяющим.
   - **Скриншоты / GIF:** обязательны для любых визуальных изменений интерфейса.

---

## 4. Правила ревью и слияния

* Ветка для создания PR: **`dev`** (все фичи создаются от `dev` и вливаются в `dev`).
* PR должен получить необходимые **Approve** от участников команды перед слиянием.
* Все комментарии и запросы изменений (`Request Changes`) должны быть закрыты/исправлены.
* Слияние выполняется методом **Squash and merge** для сохранения чистоты истории в целевой ветке.
