## 2. Граф зависимостей

```text
ADR-006 (рантайм) ──────────────► предусловие ADR-002 (ICU/tzdb в образе)
                                        │
ADR-003 (события + outbox) ─────► ADR-004 (транспорт: публикация только из релея outbox)
   │          │                            │
   │          └──► ADR-002 (payload для     └──► ADR-005 (доставка в Telegram)
   │              рендера времени в              ▲
   │              зоне читателя)                  │
   └──────────────► ADR-005 (security-события ────┘
                   пишутся в outbox)
```

Обоснование рёбер, каждое проверяемо в коде:

1. **ADR-003 → ADR-004.** ADR-004:96: публикация в RabbitMQ выполняется
   «только из релея outbox, а не из доменного кода». Релея без ADR-003 нет.
2. **ADR-003 → ADR-005.** ADR-005:155 требует событие `GITHUB_UNLINKED` «в
   `security_events` и в outbox». ADR-003:70 вводит саму таблицу outbox.
3. **ADR-003 → ADR-002.** Сейчас уведомление — готовая строка `message`
   (`schema.prisma`, модель `Notification`). ADR-002:55 требует, чтобы
   уведомление «содержало UTC-инстант и рендерилось в зоне читателя».
   Поля для инстанта нет и не появится без `payload` из ADR-003. Это жёсткая
   связь, а не стилистическая: иначе расписание нельзя отобразить в зоне
   читателя.
4. **ADR-006 → ADR-002.** ADR-006:31: «для EOL-рантайма невозможно выполнить
   требование ADR-002 о проверке таймзон после обновления базового образа —
   обновлять нечего». ADR-002:95: источник правил переходов на летнее время —
   ICU рантайма.
5. **ADR-002 ↔ ADR-005, общая миграция `User`.** ADR-002:135 и ADR-005:167
   требуют применить `timezone` и `firstLoginAt` **одной миграцией**. Это
   единственное место, где два ADR жёстко связывают друг друга.

Чего в графе нет: ADR-001 (WebSocket-жизненный цикл) не связан ни с одним из
пяти — он реализован и на порядок не влияет.

## 4. Фаза 0 — ADR-006, Node 24

**Почему первым.** Единственная фаза без входящих зависимостей, которая при
этом разблокирует ADR-002. Побочный эффект виден уже сейчас: `release.yml` и
`e2e-smoke.yml` собирают релизные артефакты на Node 20, а тесты гоняются на
24 — то есть в прод попадает сборка, проверяемая слабее, чем обычный PR
(ADR-006:21). Второй эффект: расхождение рантайма с `engines` ловит дефекты
локально. Например, на Node 25 и новее падают 13 тестов
`apps/web/src/features/media-settings/model/useMediaSettings.test.ts`:
в `beforeEach` вызывается `localStorage.clear()`, а в Node 25+ `localStorage`
объявлен как **собственное свойство `globalThis`** (`enumerable: false`,
`configurable: true`) со значением `undefined`, потому что не передан
`--localstorage-file`; Node печатает `ExperimentalWarning: localStorage is not
available because --localstorage-file was not provided`. Именно наличием
свойства, а не его значением, оно перебивает jsdom-реализацию, поэтому падение
выглядит как `TypeError: Cannot read properties of undefined (reading 'clear')`,
а не как `localStorage.clear is not a function`. В CI это не воспроизводится
(Node 24), но `engines` превратило бы это в ошибку при установке зависимостей.
Проверено 30.09.2026 на локальном Node `v26.8.2`; на Node 24 падения нет,
что подтверждает расхождение как с Node 25, а не с рантаймом в целом.

**Что это даёт и чего не даёт.** `engines` — предупреждение, а не запрет
(ADR-006:43, п. 8.5 этого документа). Фаза 0 делает расхождение явным, но
**не чинит эти 13 тестов**: на Node 25/26 локальный прогон `apps/web` останется
красным до перехода на Node 24. Утверждать обратное в критериях завершения
нельзя.

## 5. Фаза 1 — единая миграция `User`

**Почему отдельно и почему так рано.** ADR-002:135 и ADR-005:167 требуют
применить обе колонки одной миграцией: две последовательные миграции на одну
модель в конкурентных ветках дают конфликт при слиянии, который Prisma не
разрешает автоматически, и лишнее переписывание таблицы на каждом
развёртывании. Фаза 1 выполнялась до начала любой другой DB-фазы, поэтому
конфликта не возникло ни с кем. После фазы 2 (`schema.prisma` меняется в каждой
DB-фазе) добавить колонку в `User` задним числом станет заметно дороже.

Содержание:

* `User.timezone String` — IANA-идентификатор, `NOT NULL DEFAULT 'Europe/Moscow'`,
  чтобы миграция не требовала бэкфилла и не падала на непустой таблице
  (ADR-002:142).
* `User.firstLoginAt DateTime?` — остаётся nullable: для существующих
  пользователей первый вход уже произошёл, дата не выдумывается, приветственное
  уведомление им не отправляется (ADR-002:143).
* Ничего больше. Валидация таймзоны (ADR-002:47-52) — в фазе 4; заполнение из
  браузера и UI настройки — тоже в фазе 4.

**Критерий завершения.** Миграция применяется на непустой staging-таблице без
бэкфилла; `prisma migrate diff` для этой миграции не содержит переписывания
таблицы, не вызванного `NOT NULL` без значения по умолчанию.

**Выполнена 30.09.2026.** Миграция содержит ровно две строки `ADD COLUMN` и
ничего больше:

```sql
ALTER TABLE "users" ADD COLUMN "timezone" TEXT NOT NULL DEFAULT 'Europe/Moscow';
ALTER TABLE "users" ADD COLUMN "firstLoginAt" TIMESTAMP(3);
```

Критерий проверен на отдельной базе `phase1_check`: 19 миграций применены,
в `users` вставлено 25 строк, затем применена эта миграция.

* `relfilenode` таблицы `users` — `18124` до и после, то есть переписывания не
  было. Для `ADD COLUMN ... NOT NULL DEFAULT` в PostgreSQL 11+ этого и ожидаемо:
  значение вычисляется на чтении, а не переписыванием таблицы.
* Все 25 строк получили `timezone = 'Europe/Moscow'` и `firstLoginAt IS NULL` —
  бэкфилл не потребовался, приветственное уведомление существующим пользователям
  не будет отправлено (ADR-005:173).
* Вставка без `timezone` подставляет дефолт, явный `NULL` отвергается
  ограничением NOT NULL, произвольная IANA-зона принимается — валидация зоны
  остаётся в фазе 4.
* `prisma migrate diff` от состояния 19 к новой схеме показывает по `users`
  только `ADD COLUMN` без `USING` и `SET DATA TYPE`. Остальное в его выводе —
  дрейф из п. 8.10, в миграцию он намеренно не включён; позже п. 8.10 разобран,
  и после устранения дрейфа в выводе остались только три `DROP INDEX` по
  триграмм-индексам, которые Prisma не умеет описать.

Верификация не изменилась относительно базовой линии п. 9: `prisma validate`
валиден, `tsc --noEmit` в `apps/api` чист, `codegen:check` чист (контракт OpenAPI
не затронут, `User.timezone` в DTO не выводится до фазы 4), `pnpm test:api` —
49 наборов / 803 теста, `pnpm lint` — 1092 файла, `apps/web` — 60 файлов /

## 6. Фаза 2 — ADR-003 целиком

**Почему это ключевой камень.** ADR-004 и ADR-005 стоят на outbox и словаре
событий из этой фазы. Ни одна из них не начинается раньше.

**Почему именно сейчас, а не позже.** Миграция разрушительная — удаляются
`title` и `message`. Она бесплатна, пока таблица пуста, что подтверждено

2. `Notification` → `type` + `payload Json` + `renderedTitle` +

3. Таблица outbox в той же БД (ADR-003:70).
4. `NotificationDispatcher` и интерфейс канала; in-app адаптер поверх

5. Релей outbox на `@nestjs/schedule` — `ScheduleModule.forRoot()` уже

### 6.2. Побочный пункт: схемы витрины и матчмейкинга (01.10.2026)

Блокер снят. DTO из ADR-003:102 описаны Zod-схемами, а не
интерфейсами: `registerSchema` по принципу из `zod-openapi.ts`
(«ручного дублирования нет») требует именно Zod-описания в
`@packages/dto`, поэтому типы выводятся через `z.infer`, а не
объявляются отдельно. Схем получилось шесть, а не пять: общий
`PaginatedResponseDto` разворачивается в два конкретных контракта —
витрины и матчмейкинга, — потому что обобщённую схему Orval не выводит,
а `ShowcaseCardListDto` описывает отдельный по форме ответ `/showcase/my`.

| Схема в `components.schemas` | Источник |
|---|---|
| `ShowcaseCardResponseDto` | `showcaseCardResponseSchema` |
| `ShowcaseCardListDto` | `showcaseCardListSchema` |
| `PaginatedShowcaseCardsDto` | `paginatedShowcaseCardsSchema` |
| `MatchRequestResponseDto` | `matchRequestResponseSchema` |
| `PaginatedMatchRequestsDto` | `paginatedMatchRequestsSchema` |
| `UnreadMatchRequestsCountDto` | `unreadMatchRequestsCountSchema` |

Два решения, которые стоит зафиксировать:

* **Даты на проводе — ISO-строки.** Zod-схема отвечает за JSON, а не за
  Prisma, поэтому `Date` в `z.string().datetime()` не подходит. Сервисы
  отдают результат общего маппера
  (`apps/api/src/modules/showcase/showcase.mapper.ts`,
  `toShowcaseCardResponse`), который переводит четыре даты карточки через
  `toISOString()`. Для матчмейкинга маппер переиспользуется в
  `formatMatchRequest()`. JSON-контракт не изменился — раньше Nest
  сериализовал `Date` тем же `toISOString()`; изменился только
  статический тип, который Orval иначе не смогла бы вывести.
* **`PublicUserCardDto` не регистрируется отдельной схемой.** Она описана
  (`publicUserCardSchema`) и входит в `ShowcaseCardResponseDto` как
  вложенный объект, то есть в components попадает инлайн. Отдельная
  регистрация создала бы компонент, на который не ссылается ни одна
  операция, — то есть ровно тот мёртвый код, который запрещает
  `zod-openapi.ts`.

Контракты пагинации не унифицированы намеренно: у витрины и
матчмейкинга `meta` с `hasPrevPage`/`hasNextPage`, у admin — свой
`hasPreviousPage`. Сведение потребовало бы ломающего изменения одного из
контрактов.

Проверено (`openapi-generation.spec.ts`):

| Критерий | Результат |
|---|---|
| Схемы витрины и матчмейкинга в `components.schemas` | 6 компонентов на месте |
| `GET /showcase` → 200 | `$ref: PaginatedShowcaseCardsDto`; `data` — массив, `meta.hasPrevPage`/`hasNextPage` — `boolean` |
| `GET /showcase/my` → 200 | `$ref: ShowcaseCardListDto` |
| `GET /showcase/{id}` → 200, 404 | `$ref: ShowcaseCardResponseDto` |
| `GET /matchmaking/requests/unread-count` → 200 | `$ref: UnreadMatchRequestsCountDto` |
| `GET /matchmaking/requests/incoming` → 200 | `$ref: PaginatedMatchRequestsDto` |
| `POST /matchmaking/requests/{id}/accept` → 200 | `$ref: MatchRequestResponseDto` |
| Сгенерированный клиент | `showcaseControllerFindAll` → `Promise<PaginatedShowcaseCardsDto>`, `showcaseControllerFindMy` → `Promise<ShowcaseCardListDto>`, `matchmakingControllerGetUnreadCount` → `Promise<UnreadMatchRequestsCountDto>`, `matchmakingControllerFindIncoming` → `Promise<PaginatedMatchRequestsDto>`, `matchmakingControllerAccept` → `Promise<MatchRequestResponseDto>`. `Promise<void>` больше нет |

Проверка на форму обёртки в тесте — не формальность: именно `data`/`meta`
в `$ref`-схеме отличают настоящий контракт от схемы, по которой клиент
снова стал бы `Promise<void>`.

## 7. Фазы 3-6

### 7.1. Фаза 3 — ADR-004 «сшивка» (выполнена 02.10.2026)

Пункты «Что связывается между API и SSE» (ADR-004:83-89), не закрытые
коммитами `ce50f96` / `e0895e7`, сделаны все три.

**1. Словарь типов событий и Go-генерация (ADR-004:86).** Источник правды —
`packages/dto/src/realtime/sse-event.dto.ts`, а не `packages/types`, как
задумывалось в ADR: словарь SSE-контракта в `packages/types` не используется
ни одним потребителем, и второй пакет с тем же словарём развёл бы источники
правды. В словаре восемь типов, `SseEventType`, `SseEventPayloads`,
`sseEventDescriptions` и `parseSseEventPayload` — граница публикации.
`apps/realtime` получил `internal/sse/events_gen.go` с `EventType` и
`Severity`; ручные константы из `event.go` удалены.

Почему клиент и CLI стали строже, а `apps/realtime` — нет: `apps/realtime`
пересылает payload как `json.RawMessage` и имя события не сверяет, поэтому
единственное место, где опечатка ещё может быть поймана, — граница публикации
(`publishNotificationEvent`) и разбор на клиенте. Клиент при этом оставил
терпимость к `category`, `createdAt` и `read`: в семидневном потоке лежат
кадры, записанные до разделения категорий, и строгая проверка молча потеряла бы
уведомления всем, у кого осталась непроигранная история.

**2. Расхождение категорий устранено (ADR-004:87).** Визуальная severity
переехала в поле `severity`, `category` означает только доменный
`NotificationType` из БД. Ни один продюсер `severity` пока не заполняет —
поле необязательное, и это зафиксировано и в словаре, и в `SSE_SPEC.md`, чтобы
его не объявили багом при первом же кадре. CLI `--severity` добавлен и
ограничен тем же перечислением, что и словарь.

Побочно нашлась настоящая ошибка, а не стилистическая: текст кадра брался из
колонок `renderedTitle`/`renderedMessage`, которые nullable (ADR-003:58 — NULL
означает «ещё не отрендерено»), поэтому кадр `notification.new` мог уйти с
`title: null`. После включения проверки словаря такой кадр не просто уехал бы
в браузер, а уронил бы `createNotification` целиком — уже после записи строки
в БД. Кадр теперь собирается из свежего рендера; покрыто тестами, включая
повторную доставку с NULL-колонками.

**3. Мёртвый канал матчмейкинга удалён (ADR-004:89).** Удалены
`REDIS_MATCHMAKING_EVENTS_CHANNEL`, `publishMatchAcceptedEvent` и зависимость
`MatchmakingService` от `RedisService`. Удаление не сняло работавшей доставки:
подписчика канала не было нигде, а `publish` глотал ошибки, поэтому контракт
не доставлял ничего и до удаления.

**Долг, который остался после удаления.** Продюсера, заменяющего канал, в
матчмейкинге нет: `MatchmakingService` не вызывает `NotificationDispatcher`,
поэтому ни `accept`, ни авто-матч не эмитят событий. Инфраструктура замены
существует (ADR-003, фаза 2), блокер один — payload'ы
`interview.match_proposed` и `interview.slot_booked` требуют `slotId` и
UTC-инстанта, которых нет без `AvailabilitySlot` (ADR-002, фаза 4, п. 7.3
шаги 2-5 и 9). Автоматического уведомления о принятии сейчас нет ни по
SSE, ни по опросу: `refetchOnWindowFocus: false`
(`apps/web/src/shared/api/query/query-client.ts:9`), а polling
`unread-count` в проде не используется. Событие о матче появится в фазе 4.

**Решение по кодогенерации принято 02.10.2026** (ADR-004:146): генератор в
`packages/dto` рядом с источником правды, запуск
`pnpm --filter @packages/dto run generate:go`, файл коммитится в
`apps/realtime/internal/sse/events_gen.go`, актуальность проверяет новый job
`sse-events-generated` в `ci-realtime.yml`. Генератор не «слова или ничего»:
список событий исчерпывающий на обеих сторонах (`satisfies Record<SseEventType, …>`
в TypeScript и `requiredEvents` в генераторе), поэтому пропуск типа — ошибка
компиляции или падение генератора, а не тихая потеря события.

**Лимит соединений проверен (ADR-004:150).** Вкладка равна соединению:
`NotificationRealtime` смонтирован один раз в `AppProviders`,
`openNotificationStream()` вызывается в единственном эффекте, поток закрывается
в его же cleanup. Пределы: пятая вкладка пользователя — последняя, шестая
получает `429` с `Retry-After`, который клиент уважает
(`notification-stream.ts:47-56`), то есть лимит даёт задержку, а не потерю.
Лимит 20 на IP достигается за NAT офиса или CGNAT оператора и затрагивает
разных пользователей. Для расширения числа типов событий менять лимиты не
требуется.

### 7.2. Фаза 5 — ADR-004 транспорт

RabbitMQ вынесен отдельной фазой, потому что он нужен только когда
действительно требуется доставка в Telegram, и не влияет на in-app контур.

* `apps/api` — только продюсер: `amqplib` + `amqp-connection-manager`,
  консьюмера нет (ADR-004:93). Публикация только из релея outbox.
* `RABBITMQ_URL` в `configuration.ts` (секция `rabbitmq`) и в
  `env.validation.ts` (ADR-004:95) — переменная уже требуется
  `docker-compose.prod.yml:72`, но не читается приложением.
* `apps/telegram-bot` — консьюмер с ack, retry и DLQ (ADR-004:113-116):
  не более 5 попыток, backoff 1/2/4/8/16 с, DLQ `telegram.notifications.dlq`
  с хранением 7 дней, невосстановимые ошибки (`bot.ban`, `chat not found`) —
  сразу в DLQ.
* Приложение не падает при недоступности брокера; пороги алерта: возраст
  самой старой неотправленной строки outbox более 5 минут либо более 1000
  неотправленных строк (ADR-004:107).

### 7.3. Фаза 4 — ADR-002

Идёт после фаз 1, 2, 3: без миграции `User` нет `timezone`, без `payload` из
ADR-003 некуда положить UTC-инстант для рендера в зоне читателя.

Порядок работ:

1. `date-fns@4.4.0` и `@date-fns/tz@1.5.0` **точными версиями**, без `^`
   (ADR-002:78, :94). Единственная точка входа — тонкий слой в
   `packages/utils` (ADR-002:128); прямые импорты библиотеки дат в `apps/api`
   и `apps/web` не допускаются, иначе версии разойдутся между API и
   SSR-рендером и появятся расхождения в гидратации.
2. `AvailabilitySlot` с частичными индексами; `MatchRequest.slotId`;
   `durationMinutes` — в константы матчмейкинга
   (`apps/api/src/modules/matchmaking/matchmaking.constants.ts`) (ADR-002:60-61).
3. Атомарный claim слота: `updateMany` по `{ id, status: "OPEN" }`,
   `count === 0` → 409, в существующей `Serializable`-транзакции
   (`matchmaking.service.ts:318`) с ретраями на `P2034` (`:329-333`)
   (ADR-002:70-74).
4. Round-trip-проверка существования локального времени слота (ADR-002:66) —
   обязательна: `fromZonedTime`/`TZDate` на несуществующем локальном времени
   не бросают исключение, а молча сдвигают момент, поэтому декларативная
   проверка не работает.
5. Изменение авто-матча (ADR-002:109): при наличии слотов у любой из сторон
   создаётся обычная `PENDING`-заявка вместо `ACCEPTED`. Ветка кросс-инвайта —
   `matchmaking.service.ts:256-298`; перевод встречной заявки в `ACCEPTED` на
   `:276`, создание второй `ACCEPTED`-заявки на `:290`. Оговорка: `accept`
   требует `PENDING` (`:507`), поэтому сегодня ветка обходит проверку
   получателя. Смежное
   требование ADR-002:62: отдельная `InterviewSession` создаётся на этапе
   `accept` с переносом `startsAt` в `scheduledAt`. Сегодня эта связка
   отсутствует — `accept` сессию не создаёт, а `InterviewSession` создаётся
   независимым путём через `createSession`
   (`apps/api/src/modules/sessions/sessions.service.ts:237`). Поэтому
   подключать создание сессии к `accept` нужно в этой же фазе, сразу с
   частичным уникальным индексом и `Serializable`-транзакцией: иначе пара
   получает две сессии, а получатель остаётся с `PENDING`-заявкой.
6. Перевод timestamp-колонок в `timestamptz(3)` — выполняется после миграции
   фазы 1, поскольку переписывает таблицы (ADR-002:141).
7. Валидация `User.timezone` в `updateProfileSchema` **двухшаговая**: формат
   IANA, затем резолвимость через `Intl` (ADR-002:47-52). Шаг 1 обязателен:
   с ES2024 `Intl.DateTimeFormat` принимает offset-таймзоны (`+04:00`), и без
   шага 1 в поле попадёт фиксированное смещение, что нарушает правило «смещение
   не хранится». `Intl.supportedValuesOf('timeZone')` как allowlist запрещён
   (ADR-002:51).
8. `packages/i18n`: namespace `showcase` (ADR-002:129).
9. Продюсер уведомлений в `MatchmakingService` — `NotificationDispatcher`
   в `NotificationsModule` того же модуля, `dispatch` с транзакционным
   клиентом: `interview.match_proposed` при предложении слота,
   `interview.slot_booked` при его брони. Шаг идёт после пп. 2-5, потому
   что payload обоих событий требует `slotId` и UTC-инстант. Шаг 9 — это
   замена удалённого канала `matchmaking:events`, и до него уведомления о
   матче не существует ни в одном транспорте.

**Критерий завершения.** Слот, созданный на несуществующем локальном времени
в зоне владельца, отклоняется с 422; два конкурентных запроса на один слот
дают ровно один 200 и один 409; уведомление о предложении встречи рендерит
разные локальные времена для пользователей в разных зонах. Отдельно:
`MatchmakingService` вызывает `NotificationDispatcher.dispatch` в той же
`$transaction`, что и смена статуса заявки, — `interview.match_proposed` при
предложении слота и `interview.slot_booked` при брони, оба получателю. Это
закрывает долг п. 7.1: до этого продюсера у матчмейкинга не было, и кадр
`notification.new` о матче не появлялся ниоткуда.

Проверено 05.10.2026, локальный рантайм `node v24.21.0`, `pnpm 9.15.9`:

### 7.4. Фаза 6 — ADR-005

Последняя: наибольшая площадь, зависит и от outbox (ADR-003), и от доставки
в Telegram (ADR-004), и больше всего содержит неопределённостей — подтверждение
отвязки Telegram затрагивает бот.

* `SecurityEvent` — отдельная модель, security-события **не** хранятся в
  `notifications`; `NotificationType` новых значений не получает
  (ADR-005:190, ADR-003:61).
* `PROFILE_CHANGED` не содержит значений полей — только имена изменённых
  (ADR-005:120), иначе уведомление становится каналом утечки.
* `ipAddress` и `userAgent` не попадают ни в один публичный DTO и ни в
  экспортные выборки, включая административные (ADR-005:128, :182).
* Отвязка GitHub — строго в порядке ADR-005:152-159: сначала эндпоинт
  `githubId → null` с ревокацией сессий, затем событие, затем уведомление.
  Без шага 1 шаги 2-3 не регистрируются.
* Ретенция 12 месяцев; `SecurityEvent` не удаляется каскадом при soft-delete
  аккаунта (ADR-005:125-127).
* Порог `LOGIN_FROM_NEW_DEVICE`: 90 дней без успешной сессии с тем же
  нормализованным user-agent, **без** сравнения по ip (ADR-005:134-135).
* Почтовый транспорт в объём не входит, заглушек не вводится
  (ADR-005:146-148).

Разделение работ внутри фазы допустимо: запись `security_events` и
in-app-компенсирующий канал (ADR-005:140) требуют только фазы 2; доставка в
Telegram требует фазы 5. Дробить фазу на два PR стоит, только если нужно
закрыть хранение событий раньше транспорта.

## 8. Подводные камни

1. **`schema.prisma` — общий изменяемый файл.** Каждая фаза 1, 2, 4, 6 правит
   его. Две DB-фазы в параллельных ветках дают конфликт, который Prisma не
   разрешает автоматически, и `migrate` может примениться в порядке,
   не соответствующем зависимостям схемы. **DB-фазы сериализуются.**
2. **Миграция `notifications` без backfill.** ADR-003:96 обязывает остановить
   релиз при непустой таблице. Проверка обязательна как шаг релиза. После
   фазы 2 таблица начнёт наполняться, поэтому повторное применение той же
   миграции уже невозможно без backfill.
3. **Одно поле `category` — два несовместимых перечисления.** API отдаёт в SSE
   `NotificationType` (`SYSTEM|INTERVIEW|MESSAGE`), Go объявляет то же поле
   как `NotificationCategory` (`info|success|warning|error`)
   (`notifications.service.ts:195` против `sse/payload.go:12`). Значения не
   пересекаются, а валидации нет: `apps/realtime` передаёт payload как
   `json.RawMessage`, web-схема поле не читает. Любая попытка использовать
   `category` из SSE как источник истины для иконки даст пустое значение.
   Исправляется в фазе 3 переименованием визуальной severity в `severity`;
   до этого `category` нельзя считать контрактом.
4. **Словарь событий как второй источник правды.** Пока Go-константы
   продублированы руками (`event.go:14-39`), добавление типа события в
   `packages/types` без правки Go создаёт молчаливое расхождение. Это ровно тот
   класс дефекта, ради которого вводится генерация, и по условию ADR-004:142
   CI обязан это ловить — иначе генерация не нужна.
5. **`engines` не блокирует установку.** ADR-006:43: это предупреждение, а не
   запрет. Ошибку подхватит только тот, кто читает вывод, поэтому проверка
   `node-version` против `.node-version` и `engines` в CI (ADR-006:56)
   обязательна, иначе разнобой вернётся.
6. **Смена `@types/node` вместе со сменой образов** делает невозможной
   диагностику: поломка от типов и поломка от рантайма выглядят одинаково.
   ADR-006:47 требует отдельного последнего коммита.
7. **Ретенция outbox.** Релей накапливает неотправленные строки при
   недоступном брокере. ADR-004:107 задаёт пороги 5 минут / 1000 строк;
   без метрик и алерта буфер растёт незаметно.
8. **Stale `dist` монорепозитория.** `apps/web` и `apps/api` резолвят
   `@packages/*` через собранный `dist`. После изменения в `packages/ui`,
   `packages/icons` или `packages/dto` typecheck падает на отсутствующих
   экспортах, пока пакеты не пересобраны. Наблюдалось на merge `origin/dev`:
   `Volume1Icon`, `Slider`, `DeviceSettingsDto` не находились до
   `pnpm --filter @packages/... build`. Сборка пакетов — часть верификации
   фаз 2 и 4, а не отдельная забота.
9. **Расхождение `node_modules` с `pnpm-lock.yaml` ломает всю верификацию.**
   Наблюдалось 30.09.2026: `@rslib/core` был объявлен в `package.json` и
   `pnpm-lock.yaml`, но отсутствовал в `node_modules`. Последствия неочевидны
   и выглядят как регрессии фазы, которой ещё нет:
   * `pnpm --filter @packages/dto run build` падал с `rslib is not recognized`;
   * `dist` в `packages/dto` оставался без `media-settings.dto`, и
     `tsc --noEmit` в `apps/api` выдавал ~40 ложных ошибок в
     `users.service.ts` — `DeviceSettingsDto`, `Locale`, `ThemeMode`,
     `ThemePreference`, `telegramId`, `telegramLinkVerified`,
     `userDeviceSettings` «не существуют»;
   * `vitest` в `apps/web/src/features/media-settings` давал 17 падений вместо
     13: к 13 падениям `useMediaSettings` добавлялись 4 падения
     `MediaSettingsDialog.test.tsx` с `Element type is invalid: got: undefined`
     — то есть компонент не находился в устаревшем `dist` `@packages/ui`
     и `@packages/icons`.
   Затронут и сгенерированный Prisma-клиент `apps/api/src/generated/prisma`:
   его генерирует `postinstall`, поэтому без `pnpm install` он тоже устаревает.
   **Первым шагом верификации всегда идёт `pnpm install --frozen-lockfile`,
   затем сборка пакетов.** Без этого остальные команды п. 9 дают ложные
   результаты, и ошибку легко приписать текущей фазе.
10. **Дрейф между миграционными файлами и `schema.prisma`.** Обнаружено
     30.09.2026 при создании миграции фазы 1, устранено в тот же день до
     начала фазы 2. `prisma migrate dev --create-only` сгенерировал
     не два `ADD COLUMN`, а попутно:

    ```sql
    DROP INDEX "users_display_name_trgm_idx";
    DROP INDEX "users_email_trgm_idx";
    DROP INDEX "users_username_trgm_idx";
    ALTER TABLE "permissions" ALTER COLUMN "id" DROP DEFAULT,
      ALTER COLUMN "slug" SET DATA TYPE TEXT, ALTER COLUMN "name" SET DATA TYPE TEXT;
    ALTER TABLE "roles" ALTER COLUMN "id" DROP DEFAULT,
      ALTER COLUMN "slug" SET DATA TYPE TEXT, ALTER COLUMN "name" SET DATA TYPE TEXT,
      ALTER COLUMN "updatedAt" DROP DEFAULT;
    ALTER TABLE "auth_revocation_tasks" ALTER COLUMN "id" DROP DEFAULT;
    CREATE INDEX "users_telegramId_idx" ON "users"("telegramId");
    ```

    Дрейф не локальный, а закоммиченный, и складывается из трёх разных причин.

    1. `20260914120000_add_dynamic_rbac_roles_permissions` и
       `20260914140000_add_auth_revocation_tasks` написаны руками. Они создают
       `slug VARCHAR(64)`, `name VARCHAR(255)`, `id UUID NOT NULL DEFAULT
       gen_random_uuid()` и `roles.updatedAt ... DEFAULT CURRENT_TIMESTAMP`,
       тогда как `schema.prisma` объявляет `String` (то есть `TEXT`) и не ждёт
       DB-дефолтов: UUID выдаёт клиент Prisma, `updatedAt` ведёт `@updatedAt`.
       Инициализация `20260814182859_init` DB-дефолтов на `id` не добавляла, и
       4 модели из 6 их не имеют — то есть дефолты в трёх таблицах были
       отклонением от конвенции репозитория, а не её частью. В приложении нет
       ни одного `$executeRaw`/`$queryRaw`, а `slug` приходит только из ентумов
       `SystemRole`/`PermissionSlugs` через `seed-admin.ts`, поэтому дефолты
       никем не используются.
    2. `20260914160000_add_trigram_search_indices` создаёт `pg_trgm` и три
       GIN-индекса с `gin_trgm_ops`. Миграция закоммичена и применяется Prisma
       штатно, но описать такой операторный класс в `schema.prisma` невозможно:
       Prisma поддерживает `type: Gin`, но не `gin_trgm_ops`. Индексы навсегда
       останутся для неё лишними.
    3. `@@index([telegramId])` был объявлен в схеме, но ни одна миграция его не
       создавала: в БД есть только уникальный `users_telegramId_key` из
       `20260922103100_add_telegram_id_unique_index`.

    **Почему это опасно.** Такой SQL, попав в коммит, удаляет три индекса полнотекстового
    поиска по пользователям и переписывает таблицы `permissions` и `roles` — то
    есть тихо расширяет DB-фазу за пределы её объявленного объёма. Ровно то, от
    чего предостерегает п. 8.1.

    **Что сделано в фазе 1.** Миграция записана вручную ровно двумя строками
    `ADD COLUMN`; посторонний SQL из сгенерированного файла удалён. Правку
    `20260914120000` сделать нельзя — миграция уже применена во всех
    окружениях, Prisma хранит её хеш и ручная правка даст «migration modified
    after applying».

    **Дрейф устранён 30.09.2026, до начала фазы 2.**

    | Причина | Решение | Изменение в БД |
    | --- | --- | --- |
    | `VARCHAR(64)/(255)` против `String`=`TEXT` | в `schema.prisma` добавлены `@db.VarChar(64)` и `@db.VarChar(255)`: ограничение длины сохраняется как осмысленная защита от мусорных slug | нет, схема подтянута под уже применённую БД |
    | мёртвые DB-дефолты на `id` (3 таблицы) и `roles.updatedAt` | дефолты сняты миграцией `20260930124640_drop_db_generated_defaults` по конвенции `init` | только `ALTER COLUMN ... DROP DEFAULT`, без переписывания таблиц |
    | `@@index([telegramId])` без индекса в БД | декларация убрана: уникальный `users_telegramId_key` уже обслуживает и равенство, и сортировку по той же колонке | нет, убран лишний `btree`-индекс на каждую вставку в `users` |
    | `gin_trgm_ops` | устранить нельзя, принято осознанно | нет |

    Проверка: `prisma migrate diff --from-config-datasource --to-schema` даёт
    ровно три операции, и все три — `DROP INDEX` по триграмм-индексам; посторонних
    `ALTER`/`CREATE` ноль. Таблицы не переписывались: `relfilenode` у `roles`,
    `permissions`, `auth_revocation_tasks` не изменились. Вставка роли через
    Prisma без `id` проходит (UUID выдаёт клиент), `updatedAt` заполняется,
    `slug` длиной 64 принимается, длиной 65 отклоняется. API 49 сьютов / 803
    теста, e2e 20/21 сьютов — с единственным известным `E2E-04`.

    **Остаточный риск, принятый осознанно.** Любой будущий
    `prisma migrate dev --create-only` по-прежнему предложит удалить три
    триграмм-индекса. CI-проверку на `DROP INDEX` решено не вводить, поэтому
    перед коммитом каждой сгенерированной миграции эти три строки нужно вырезать
    руками. Это единственный известный остаточный пункт дрейфа.
