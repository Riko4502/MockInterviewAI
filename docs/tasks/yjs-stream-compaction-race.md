# Проблема потери дельт при XTRIM MINID в Redis Stream (`yjs.snapshot`)

Файл для анализа архитектурной уязвимости, описания причин возникновения гонки и вариантов безопасной реализации компактизации истории документов Yjs в Redis.

---

## 📌 Описание проблемы (Root Cause)

В текущей реализации совместного редактирования Yjs в сервисе `apps/realtime` и провайдере `apps/web` обнаружена критическая проблема целостности данных при компактизации стрима:

1. **Суть механизма компактизации:**
   - Когда размер истории правок возрастает, клиент (`RealtimeYjsProvider`) сериализует текущее состояние документа `Y.Doc` через `Y.encodeStateAsUpdate` и отправляет событие `yjs.snapshot` на сервер.
   - Сервер в методе `CompactTaskStream` (`apps/realtime/internal/storage/redis.go`) делает `XADD` снимка в Redis Stream `session:{id}:task:{key}:updates` и получает новый идентификатор `snapshotID`.
   - Сразу после этого вызывается `r.client.XTrimMinID(ctx, streamKey, snapshotID)`.

2. **Сценарий гонки и потери данных:**
   - Клиент **B** отправляет правку `yjs.update`. Сервер помещает её в оперативную очередь `saveQueue` и рассылает по WebSocket клиенту **A**.
   - До момента получения или локального применения этой дельты клиент **A** (или интервьюер) достигает порога `compactionThreshold` и формирует `yjs.snapshot`. Этот снимок содержит **только те правки, о которых знал клиент A на момент вызова `sendSnapshot`**.
   - Фоновый таймер `saveQueue` (с интервалом 50 мс) вызывает `FlushSync` и записывает дельту клиента **B** в стрим (например, с ID `100-0`).
   - Горутина обработки снимка в `room.handleBroadcast` записывает `snapshot` в стрим (получает ID `101-0`) и вызывает `XTRIM MINID 101-0`.
   - **Результат:** Запись `100-0` (дельта клиента B) удаляется из Redis Stream через `XTRIM`, хотя в теле `snapshot` её не было!
   - Новые участники сессии или пользователи, обновляющие страницу, получают через `sendYjsInit` только `snapshot` и последующие дельты — правка клиента **B** навсегда исчезает из истории документа.

3. **Усугубляющие факторы:**
   - **Множественные параллельные инициаторы:** В `RealtimeYjsProvider.ts` счётчик `updatesSinceCompaction` увеличивается как при отправке собственных правок (`doc.on('update')`), так и при получении входящих сетевых дельт в `handleMessage`. В результате порог достигается всеми участниками комнаты одновременно, порождая шторм конкурирующих запросов `yjs.snapshot`.
   - **Неатомарность операций:** `XADD` и `XTRIM MINID` выполняются двумя отдельными вызовами Redis без транзакции или Lua-скрипта.

---

## 🛠 Варианты решения

### Вариант 1: Client-Tracked `upToStreamId` + Атомарный Lua-скрипт

Клиент передаёт серверу информацию о том, до какой именно записи в стриме его снимок гарантированно актуален.

#### Схема работы:
1. **Передача ID стрима клиенту:**
   - В событии `yjs.init` сервер возвращает массив дельт с их Redis Stream ID (например, `{ id: string, data: string }[]`).
   - При подтверждении входящих дельт через `yjs.ack` или периодический sync-статус сервер передаёт последний записанный Stream ID.
2. **Отправка снимка:**
   - В DTO `YjsSnapshotPayload` добавляется обязательное поле `upToStreamId: string`.
   - Клиент формирует снимок только по тем дельтам, которые уже получили подтверждённый `streamId`, и передаёт `upToStreamId`.
3. **Атомарная компактизация в Redis (Lua-скрипт):**
   - Сервер выполняет единый Lua-скрипт:
     ```lua
     -- KEYS[1]: stream key
     -- ARGV[1]: snapshot_data
     -- ARGV[2]: up_to_stream_id
     local snapshot_id = redis.call('XADD', KEYS[1], '*', 'data', ARGV[1])
     redis.call('XTRIM', KEYS[1], 'MINID', ARGV[2])
     return snapshot_id
     ```
   - Записи, появившиеся после `upToStreamId` (включая дельту B), сохраняются в стриме после снимка и накатываются поверх него при следующем `yjs.init`.
4. **Ограничение инициатора на клиенте:**
   - Только один участник (роль `interviewer` или комнатный координатор) имеет право отправлять `yjs.snapshot`.
   - Исключить инкремент `updatesSinceCompaction++` на входящие сообщения в `handleMessage`.

#### Плюсы:
- Работает без необходимости парсить Yjs бинарники на Go-сервере (клиент сам сериализует сжатый `Y.Doc`).
- Гарантирует сохранность дельт, пришедших во время формирования снимка.

#### Минусы и сложности:
- Живые дельты `yjs.update` транслируются другим клиентам с минимальной in-memory задержкой (< 1 мс), до того как попадают в Redis Stream через батч `saveQueue` (50 мс). Привязка каждой дельты к `streamId` усложняет протокол подтверждений.

### Вариант 2: Server-Side Compaction в сервисе с полным состоянием (Backend Worker)

Полный перенос ответственности за компактизацию со стороны браузерных клиентов на доверенный бэкенд.

#### Схема работы:
1. Клиенты больше не генерируют и не отправляют событие `yjs.snapshot`. Клиенты только отправляют инкрементальные дельты `yjs.update`.
2. Фоновый воркер (например, задача в `apps/api` на NestJS / BullMQ / cron, где доступна официальная npm-библиотека `yjs`):
   - Раз в N минут (или по событию превышения длины стрима > 200 записей через `XLEN`) запрашивает срез истории `XRANGE streamKey - + COUNT 100`.
   - Берёт срез записей до ID `X`.
   - Вызывает `Y.mergeUpdates(deltas)` из пакета `yjs` в Node.js рантайме.
   - Атомарно записывает полученный snapshot в начало стрима и удаляет записи `<= X` через транзакцию/Lua.

#### Плюсы:
- **100% надёжность:** Браузерные клиенты лишены возможности случайно или намеренно обрезать историю или передать битые байты.
- Go realtime-сервер остаётся легковесным релеем без знания внутренней структуры CRDT.
- Никаких гонок между клиентами: компактизация происходит строго последовательно на бэкенде.

#### Минусы:
- Требуется интеграция с Node.js процессом (`apps/api`), так как в Go нет нативной реализации `Y.mergeUpdates`.

---

### Вариант 3: Single-Leader Debounced Compaction (компромиссный вариант)

Если сохранять генерацию снимка на клиенте, но минимизировать вероятность конкуренции:

1. **Единственный инициатор:**
   - Право на отправку снимка имеет строго `interviewer` (уже обеспечено валидацией в `client.go` и `room.go`).
   - В `RealtimeYjsProvider` вызов `sendSnapshot` разрешается только при наличии флага `isInterviewer === true`.
2. **Debounce / Idle Window:**
   - Снимок отсылается не сразу по достижении порога дельт, а только после паузы в редактировании (например, 5–10 секунд отсутствия локальных и входящих дельт).
   - В момент тишины `saveQueue` гарантированно сброшен в Redis, и риск параллельной записи дельты стремится к нулю.
3. **Безопасный XTRIM:**
   - Сервер фиксирует ID последней записи стрима на момент начала обработки снимка и обрезает только до неё, а не до самого `snapshotID`.

---

### Вариант 4: Временное отключение обрезки стрима (`Quick Win`)

Для текущей стадии проекта и предотвращения потери данных на реальных собеседованиях:
- Сессии собеседований длятся 1–2 часа.
- Количество правок редко превышает несколько тысяч записей (несколько мегабайт в памяти Redis).
- У каждого ключа стрима уже настроен TTL 24 часа (`StreamTTL = 24 * time.Hour`).
- **Действие:** Временно закомментировать/отключить вызов `XTrimMinID` в `CompactTaskStream` или отключить триггер `sendSnapshot` в `RealtimeYjsProvider`. Redis Stream сохранит все дельты за время сессии, исключив риск удаления кода кандидата.
