# План реализации: безопасная отвязка аккаунтов по ADR-005 (backend/API)

## Статус

Не реализовано.

## Цель плана

Пошагово реализовать backend-флоу безопасной отвязки Telegram/GitHub по [ADR-005](../../adr/ADR-005.md): подтверждение отвязки Telegram одноразовым кодом из Telegram, ревокация сессий (инкремент `generation`), аудит SecurityEvent, security-уведомления, отдельные эндпоинты отвязки.

## Зависимости

- **Prisma**: доступ к моделям User, SecurityEvent, при необходимости модель токенов для одноразовых кодов.
- **Redis** (предпочтительно) для хранения одноразовых токенов с TTL.
- **Telegram модуль**: отправка одноразового кода в Telegram.
- **SecurityEvents модуль**: фиксация событий `TG_UNLINKED`, `GITHUB_UNLINKED`.
- **Notifications модуль**: отправка security-уведомлений.
- **Sessions/Auth**: механизм ревокации сессий через инкремент `generation`.

## 2. Дизайн API (эндпоинты)

Предполагаемые эндпоинты (уточнить по конвенциям проекта):

### Отвязка Telegram (подтверждаемый флоу)
- `POST /auth/telegram/unlink/request` или `POST /users/me/telegram/unlink/request` — запрос генерации одноразового токена для отвязки Telegram. Возвращает информацию о том, что код отправлен в Telegram.
- `POST /auth/telegram/unlink/confirm` или `POST /users/me/telegram/unlink/confirm` — подтверждение отвязки с одноразовым кодом. Тело: `{ token, code }` или аналогичное. При успехе выполняет отвязку + ревокацию сессий + аудит.

Альтернативное размещение — в `UsersController` (эндпоинты `/users/me/...`) либо в `AuthController`. Следовать существующей структуре проекта.

### Отвязка GitHub
- `POST /users/me/github/unlink` (или `DELETE /users/me/github`) — немедленная отвязка с ревокацией сессий (если не требует подтверждения). Согласно ADR-005 GitHub-отвязка также должна включать ревокацию сессий и событие безопасности.

Точные пути зафиксировать в OpenAPI.

## 3. Модель данных

### Одноразовый токен для отвязки Telegram
При необходимости создать структуру хранения:
- Key: `telegram:unlink:token:{tokenId}` или хранить хэш токена
- Поля: userId, tokenHash, codeHash (если код хранится хешированным), expiresAt, used (boolean), attempts (int)
- TTL: согласно ADR-005 (уточнить значение)

Альтернатива — модель в Prisma с `expiresAt` + индексом.

### Обновления в Prisma
- User: используется `generation` (уже есть) — инкремент при отвязке.
- SecurityEvent: типы `TG_UNLINKED`, `GITHUB_UNLINKED` (уточнить enum в схеме/коде).

### 4.2. Сервисная логика (UsersService/AuthService)

- [ ] Метод генерации одноразового токена для отвязки Telegram:
  - Валидация: пользователь привязан к Telegram? Если нет — ошибка.
  - Генерация криптографически стойкого токена + кода (6-цифровой или иное).
  - Сохранение с TTL.
  - Отправка кода в Telegram пользователю.

- [ ] Метод подтверждения отвязки Telegram:
  - Валидация токена: существует, не истёк, не использован.
  - Валидация кода: совпадает.
  - В транзакции:
    - Сброс `telegramUsername = null`, `telegramId = null` (если есть) у пользователя.
    - Инкремент `generation++`.
    - Пометка токена как использованного.
    - Создание SecurityEvent `TG_UNLINKED`.
  - Отправка security-уведомления.
  - Возврат результата.

- [ ] Метод отвязки GitHub:
  - Валидация: пользователь привязан к GitHub? Если нет — ошибка.
  - В транзакции:
    - Сброс `gitUrl = null`, `githubId = null` (если есть) у пользователя.
    - Инкремент `generation++`.
    - Создание SecurityEvent `GITHUB_UNLINKED`.
  - Отправка security-уведомления.
  - Возврат результата.

- [ ] Токен и код генерировать криптографически случайными (например, `crypto.randomBytes`).
- [ ] Хешировать токен/код при хранении (не хранить в открытом виде).
- [ ] Установить разумный TTL (например, 5-10 минут) и лимит попыток ввода кода.
- [ ] Помечать токен как использованный сразу после успешного подтверждения (одноразовость).
- [ ] Блокировать повторное использование.
- [ ] Не логировать токен, код в plaintext.

## 9. Примечания

- **Потребители контракта.** После генерации OpenAPI эндпоинты используются фронтендом: [спецификация UI-флоу](../../frontend/specs/features/update-profile/security-unlink-frontend-spec.md), [план](../../frontend/specs/features/update-profile/security-unlink-adr-005-plan.md), «зонтичная» [спека](../../frontend/specs/features/update-profile/security-unlink-adr-005-spec.md).
- **Не изменять `PATCH /profile/me`** для операций отвязки — сохранить обратную совместимость. Новые эндпоинты — единственный путь для безопасной отвязки по ADR-005.
- **Транзакционность**: при создании SecurityEvent и обновлении User лучше использовать транзакцию там, где это логично.
- **Redis vs DB**: для одноразовых токенов с коротким TTL Redis предпочтительнее (авто-экспирация). Если Redis недоступен в окружении — рассмотреть хранение в БД с `expiresAt` + фоновую очистку.
- **GitHub отвязка**: в отличие от Telegram, может не требовать код-подтверждения — но требует ревокации сессий и аудита (согласно ADR-005).
