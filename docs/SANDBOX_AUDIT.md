# Аудит архитектуры и ограничения онлайн-песочницы (Sandbox)

В данном документе зафиксирован технический аудит текущей реализации песочницы (`apps/web/src/features/sandbox`), выявленные архитектурные ограничения, риски и дорожная карта (roadmap) по их устранению.

---

## 1. Совместное редактирование (Concurrency & Realtime)

### 1.1. Стратегия Last-Write-Wins (LWW) вместо CRDT / OT
* **Текущее состояние:** Синхронизация кода в `useSandboxRealtime.ts` передаёт **полный текст файла** (`code-update`) при каждом изменении локального редактора.
* **Проблема:** При одновременном вводе двумя и более участниками (интервьюер и кандидат) более позднее сообщение перезаписывает весь буфер собеседника. Возникают гонки ввода, потеря набранных символов и мерцание курсора.
* **Решение:** Переход на **CRDT** (Conflict-free Replicated Data Types), например **Yjs** (`yjs`, `y-monaco`, `y-websocket`) или **Automerge**. Это обеспечит посимвольное слияние изменений без блокировок и конфликтов.

### 1.2. Смещение абсолютных позиций курсоров
* **Текущее состояние:** Позиция курсора передаётся абсолютными координатами `{ line, column }`.
* **Проблема:** Если первый участник вставит строку в начале файла, курсор второго участника в конце файла визуально останется на прежнем номере строки, указывая на неверный фрагмент кода.
* **Решение:** Привязка курсоров к относительным позициям документа через механизм awareness/presence в Yjs.

## 2. Выполнение и тестирование кода (Code Execution)

### 2.1. Отключённый запуск кода (Run Code)
* **Текущее состояние:** Кнопка «Run Code» в `SandboxHeaderActions.tsx` заблокирована (`disabled={true}`).
* **Проблема:** Пользователь не может запустить написанный алгоритм и проверить решение на тестах внутри песочницы.
* **Решение:** 
  1. Реализовать сквозной клиентский вызов к сервису `apps/code-runner` через API шлюз (`apps/api`).
  2. Поддержать стриминг `stdout`/`stderr` и результатов прогона тестов в консольную панель (`SandboxConsolePanel`).
  3. Обеспечить безопасность изоляции выполнения (Docker / gVisor / Firecracker / Isolate).

---

## 3. Медиа-связь и видеовиджет (WebRTC & LiveKit)

### 3.1. Ограничения резервного P2P Mesh режима
* **Текущее состояние:** Хук `useWebRTC.ts` реализует прямое P2P соединение 1:1.
* **Проблема:** Топология Full Mesh не масштабируется, если к собеседованию подключаются наблюдатели, HR или второй интервьюер (нагрузка на сеть растёт как $O(N^2)$).
* **Решение:** Использовать LiveKit SFU как основной режим для групповых комнат, а P2P оставить только в качестве fallback 1:1.

### 3.2. Синтетические медиапотоки и управление состоянием Mute/Unmute
* **Текущее состояние:** 
  - В основном режиме LiveKit (`useLiveKitRoom.ts`) состояние публикации и отключения звука/видео управляется через специализированные методы SDK (`setMicrophoneEnabled`, `setCameraEnabled`, события `TrackMuted` / `TrackUnmuted`).
  - В резервном режиме P2P 1:1 (`useWebRTC.ts`) переключение микрофона и камеры выполняется на уровне нативных свойств `MediaStreamTrack.enabled`, а актуальное состояние передаётся удалённой стороне через сигналинг (`media-state`).
  - При отсутствии физической камеры генерируется заглушка через Canvas (20 FPS) и синтетический звук через `OscillatorNode`.
* **Проблема:** Нерациональный расход CPU/GPU на рендеринг искусственного видео/аудио Canvas, когда камера и микрофон выключены.
* **Решение:** 
  1. В режиме **LiveKit SFU**: использовать штатное LiveKit Track Mute/Unmute API для остановки передачи медиа на сервер без генерации синтетических потоков.
  2. В режиме **P2P 1:1 fallback**: опираться на `MediaStreamTrack.enabled` и сигналинг `media-state`, отображая UI-плейсхолдеры на клиенте без создания постоянных Canvas-потоков.

## 4. Модель данных и управление состоянием

### 4.1. Статический каталог задач
* **Текущее состояние:** Задачи захардкожены в статическом файле `tasks.ts` на клиенте.
* **Проблема:** Невозможно добавлять новые задачи без деплоя фронтенда; нет поддержки фильтрации, категорий, тегов и серверной валидации тестов.
* **Решение:** Загрузка каталога задач и тестовых наборов через NestJS REST API / TanStack Query с кэшированием.

### 4.2. Отсутствие истории изменений и таймлайна интервью (Code Playback)
* **Текущее состояние:** В Redis сохраняется только последнее состояние кода комнаты (`session:code:<id>`).
* **Проблема:** Интервьюер не может просмотреть историю правок кандидата после интервью и оценить динамику решения задачи.
* **Решение:** Логирование diff-снимков или Yjs update-векторов в S3 / PostgreSQL для последующего воспроизведения таймлайна (code playback).

## 5. AI-подсказки и ассистент

### 5.1. Статический список подсказок
* **Текущее состояние:** Подсказки берутся из предопределённого массива строк в конфигурации задачи.
* **Проблема:** Подсказки не учитывают фактический контекст и код кандидата (например, синтаксические ошибки или неоптимальную асимптотику).
* **Решение:** Интеграция LLM-ассистента с потоковым анализом текущего AST и контекстными наводящими вопросами.

## 6. Технический анализ и подводные камни текущей реализации (Gotchas & Edge Cases)

### 6.1. Служба времени на клиентах и Clock Skew при Last-Write-Wins
* **Текущее состояние:** Поле `Version` снимка генерируется на стороне браузера через `Date.now()`.
* **Подводный камень:** Если системные часы одного из клиентов (например, кандидата) спешат на 2–5 секунд относительно часов интервьюера, любые правки кандидата будут автоматически иметь более высокий `Version` и подавлять правки собеседника при условном сохранении в Redis (`codePayload.Version > lastSavedVersion`).
* **План устранения:** Использование логических часов (Lamport Timestamps) или векторных часов (Vector Clocks) на уровне WebSocket-хаба Go, а в целевой архитектуре — переход на CRDT (Yjs).

### 6.2. Длительный отказ Redis и сохранение в памяти
* **Текущее состояние:** При недоступности Redis воркер `codeSaveWorker` складывает последний снимок в `pendingCodeState` и повторяет попытку с экспоненциальным backoff.
* **Подводный камень:** Пока Redis не восстановился, данные удерживаются исключительно в RAM процесса Go. В случае перезапуска пода (OOMKilled, deployment) в период сбоя Redis несохранённый снимок будет утерян.
* **План устранения:** Наличие локального WAL (Write-Ahead Log) на диске пода или аварийного сброса в объектное хранилище (S3/PostgreSQL).

### 6.3. Политика автовоспроизведения браузеров (Autoplay Policy) для входящих звонков
* **Текущее состояние:** Получатель автоматически выполняет `livekit.connect()` и открывает медиавиджет при получении сигнала `call-started`.
* **Подводный камень:** В браузерах с жесткими политиками медиа (Safari, iOS WebKit, Chrome без предварительного взаимодействия) автовоспроизведение входящего аудиопотока блокируется браузером до явного пользовательского жеста (User Gesture).
* **План устранения:** Обрабатывать Promise rejection от `audio.play()` и отображать в UI кнопку-баннер *"Включить звук собеседника"*.

### 6.4. Отсутствие бесшовного переключения (Failover) LiveKit ↔ P2P посреди звонка
* **Текущее состояние:** При инициации звонка сначала опрашивается LiveKit SFU; при ошибке подключения происходит откат на WebRTC P2P.
* **Подводный камень:** Если LiveKit SFU разрывает соединение уже во время активного разговора (сетевой сбой медиасервера), автоматический бесшовный переход на P2P без прерывания сессии не выполняется — требуется ручной перезапуск звонка.
* **План устранения:** Добавить watchdog состояния `ConnectionState.Disconnected` во время `isInCall` с автоматической попыткой согласованного fallback-звонка через `webrtc.startCall()`.

### 6.5. Вытеснение ID из кольцевого буфера дедупликации (Buffer Eviction)
* **Текущее состояние:** `seenMessageIdsRef` хранит последние 1000 ID сообщений для фильтрации дубликатов между `WebSocket` и `BroadcastChannel`.
* **Подводный камень:** При непрерывном быстром наборе кода и перемещении курсоров генерируются десятки сообщений в секунду, и 1000 ID могут быть вытеснены за 1–2 минуты. Если WebSocket-сообщение задержалось в сети из-за packet loss или повторного подключения, старый ID может быть уже вытеснен из кэша.
* **План устранения:** Сочетать дедупликацию по `id` со строгой монотонностью версий (`codePayload.Version > localAppliedVersion`).

### 6.6. Исполнение Monaco Language Services в основном потоке (Main Thread)
* **Текущее состояние:** `initMonaco()` подгружает локальный бандл `monaco-editor`.
* **Подводный камень:** Без настройки отдельных Web Workers (`ts.worker.js`, `editor.worker.js` через `MonacoEnvironment.getWorkerUrl`) парсинг TypeScript AST и подсветка выполняются в основном потоке JS, что может вызывать микрофризы UI на больших файлах (>1000 строк).
* **План устранения:** Настроить бандлер (Vite / Next.js Webpack) для раздачи воркеров Monaco в изолированных Web Worker потоках.

## Сводная дорожная карта (Roadmap)

| Приоритет | Направление | Задача | Ожидаемый эффект |
| :--- | :--- | :--- | :--- |
| 🔴 **Высокий** | Коллаборация | Внедрение **Yjs + Monaco** | Исключение конфликтов, гонок LWW и потери кода при параллельном вводе |
| 🔴 **Высокий** | Выполнение | Интеграция с `apps/code-runner` | Рабочий запуск кода и автотестов для всех поддерживаемых языков |
| 🟡 **Средний** | Медиа | Watchdog & Autoplay Unmute UI | Надежное воспроизведение медиа в Safari и автоматический failover |
| 🟡 **Средний** | Производительность | Monaco Web Workers | Вынос языковых сервисов Monaco из главного UI потока |
| 🟡 **Средний** | Задачи | Серверный каталог задач в `apps/api` | Динамическое добавление задач, скрытые тест-кейсы |
| 🟡 **Средний** | Аналитика | История версий (Code Playback) | Возможность ретроспективы и ревью процесса написания кода |
| 🟢 **Низкий** | AI | Контекстные подсказки через LLM | Адаптивная помощь кандидату во время решения |
