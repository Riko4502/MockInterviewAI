# ADR-005: Security-уведомления и аудит событий безопасности

## Статус
Принято

## Контекст и проблема

Требовался набор уведомлений по безопасности аккаунта:

1. При первой авторизации — приветственное уведомление.
2. При смене пароля — уведомление; если привязан Telegram — сообщение в бот с предупреждением «если это не вы, напишите нам».
3. При изменении профиля, удалении привязки Telegram или GitHub — уведомление. При удалении Telegram-привязки — сначала сообщение в Telegram, затем удаление, либо удаление только по коду из Telegram.

Проверка репозитория выявила, что каждый пункт упирается в отсутствующую инфраструктуру.

### Аудит событий безопасности отсутствует полностью

В проекте нет ни модели, ни сервиса аудита. Поиск по `audit`, `activityLog`, `securityEvent`, `loginHistory`, `firstLoginAt`, `lastLoginAt`, `emailVerifiedAt` не даёт совпадений в коде. Единственное упоминание — незавершённый план в `docs/tasks/email-service.md:99-121` с матрицей событий и интерфейсом `SecurityAlertProps`, из которых не реализовано ничего.

В `User` (`apps/api/prisma/schema.prisma:39-80`) есть `createdAt` (`:62`), `generation` (`:60`), `isActive`/`deactivatedAt` (`:46-47`), `deletedAt` (`:59`) — но ни одного поля, фиксирующего факт и обстоятельства входа.

### «Первая авторизация» нечем определить

Нет `firstLoginAt`. Ближайший прокси — `User.createdAt`. При этом `loginUser` (`apps/api/src/modules/auth/auth.service.ts:328`) — единая точка входа, через которую проходят и password-login, и GitHub OAuth, и Telegram OAuth.

### IP и User-Agent не собираются нигде

`request.ip` читается ровно в одном месте — `AuthThrottlerGuard` (`apps/api/src/modules/auth/guards/auth-throttler.guard.ts:26-35`) — и сразу выбрасывается. Ни IP, ни UA, ни устройство не сохраняются. В `AuthSession` (`apps/api/src/modules/auth/services/auth-session.service.ts:8-16`) только `userId`, хеш refresh-токена, `createdAt`, `lastUsedAt`, `generation`.

Сигнатура `changePassword(userId, dto)` (`auth.service.ts:501`) не принимает `Request`, поэтому контекст запроса в неё не попадает. Уведомление «если это не вы» без указания, откуда и когда, практически бесполезно.

### Смена пароля уничтожает все сессии до того, как уведомление будет показано

`changePassword` (`auth.service.ts:501-575`) в одной `$transaction` обновляет `passwordHash` и делает `generation: { increment: 1 }` (`:541`), создаёт `AuthRevocationTask` (`:550`), затем вызывает `revokeSessionsWithRetry` (`:562`) и публикует отзыв в `auth:revocations`, на что Go-сервис выкидывает живые SSE-соединения.

Следствие: **in-app уведомление о смене пароля недостижимо по определению** — к моменту его создания пользователь разлогинен на всех устройствах. Реальные каналы для security-событий — только Telegram и email.

### Email-транспорта нет

`apps/api/src/modules/mail/mail.service.ts:22-38` — единственная отправка: `logger.log("[MOCK EMAIL] ... Token: <raw token> ... Reset URL: <url>")`. Реального SMTP/SES нет, зависимости `nodemailer`/`resend`/`sendgrid` нет. Дополнительно: `webUrl` резолвится через `app.webUrl`/`webUrl`, которых нет в `configuration.ts`, поэтому в проде ссылки ведут на `localhost:3000`. И отдельно, не в рамках задачи: сырой reset-токен пишется в логи на уровне `log` — это секрет в логах.

### Отвязка Telegram происходит мгновенно, подтверждение отправить некуда

`TelegramService.unlink` (`apps/api/src/modules/telegram/telegram.service.ts:174-185`) немедленно выполняет `updateMany` с `data: { telegramChatId: null, telegramLocale: null }` (`:177`). Отправить «привязка отвязана» после этого физически некуда — адресата больше нет.

Дополнительно:

* Эндпоинт `POST /api/v1/telegram/unlink` — `@Public() @UseGuards(InternalServiceKeyGuard)` (`telegram.controller.ts:115-130`), вызывается **только ботом** по `chatId` из тела. Пользователь из веба сегодня не может отвязать Telegram вообще.
* `unlink` **не** трогает `telegramId` и `telegramLinkVerified`, **не** ревокает сессии, `generation` не увеличивается. То есть отвязка Telegram сейчас — не security-событие, и уведомление обещало бы защиту, которой нет.
* `telegramId` и `telegramLinkVerified` в этом флоу не пишутся; `telegramUsername` читается для DTO (`telegram.service.ts:307`), но не сохраняется — бот всегда получает `null`.
* `telegramLinkVerified` выставляется в `UsersService.linkTelegram` (`apps/api/src/modules/users/users.service.ts:265`).

### Отвязки GitHub не существует

`githubId` пишется только в `UsersService.create` (`users.service.ts:217`) и в `GithubOAuthService.findOrCreateUser` (`apps/api/src/modules/auth/services/github-oauth.service.ts:208-211`). Ни один код не устанавливает его в `null`. Эндпоинта, DTO или сервисного метода для отвязки нет.

Это не «не хватает уведомления», а дыра: компрометация GitHub-аккаунта не отзывается. `resetPassword` (`auth.service.ts:814-838`) очищает `telegramId`/`telegramUsername` при `!telegramLinkVerified` (`:822`), но **не** трогает `githubId` — то есть смена пароля не разрывает GitHub-доступ.

### Free-text `telegramUsername` в профиле

`PATCH /profile/me` (`users.service.ts:371`, запись в `:399`) позволяет записать **любой** `telegramUsername`, и он отображается в публичном профиле. При этом `telegramId` в `updateProfileSchema` отсутствует — подтверждения владения нет. Если такое изменение попадёт в уведомление, оно легитимизирует подделку; кроме того, пользователь может флудить сам себя циклами PATCH.

## Рассмотренные варианты

### Где хранить security-события

1. **Добавить `SECURITY` в `NotificationType` и писать в ту же таблицу.** Отклонено: разные семантика чтения, политика хранения (ip/ua/geo — персональные данные) и отношение к удалению аккаунта. «Прочитано» для маркетингового уведомления и «прочитано» для сообщения «ваш пароль изменён, это были вы?» — не одно и то же действие.
2. **Отдельная модель `SecurityEvent` + отдельный поток доставки.** Принято.

### Как подтверждать отвязку Telegram

1. **Отправить сообщение в Telegram, затем отвязать.** Отклонено: текущий `unlink` зануляет `telegramChatId` немедленно, отправка после невозможна; а отправка до неё — это уведомление, а не подтверждение намерения. Злоумышленник, вошедший в веб-кабинет, получил бы сообщение «ваш Telegram отвязан» как уже свершившийся факт.
2. **Подтверждение кодом в самом Telegram.** Принято. Запрос отвязки создаёт одноразовый токен с TTL, бот показывает его владельцу чата, и только после предъявления кода привязка снимается. Подтверждение по умолчанию идёт в тот канал, который и снимается.

### Канал доставки

1. **In-app уведомление как основной.** Отклонено: недостижимо при смене пароля из-за `generation` (см. выше). Как дополнительный канал — используется, но не как основной.
2. **Telegram-пуш как основной.** Отклонено: работает только у тех, кто привязал Telegram; требует отдельного канала отката, если отвязка — как раз инициированное событие.
3. **Email как основной, Telegram — дополнительный.** Отклонено **как решение текущей задачи**: почтового транспорта в проекте нет, и принять его как основной канал значит принять зависимость от незавершённой работы. Email остаётся основным каналом **после** реализации `docs/tasks/email-service.md`; в текущем объём входит только Telegram плюс компенсирующий in-app при следующем входе.

## Принятое решение

### Модель аудита

* Вводится модель `SecurityEvent` (`@map("security_events")`): `id`, `userId`, `type` (из фиксированного перечисления), `ipAddress?`, `userAgent?`, `metadata Json?`, `createdAt`. События **не** удаляются каскадом вместе с пользователем — это хранение персональных данных и требует отдельной политики ретенции.
* Типы событий как минимум: `ACCOUNT_REGISTERED`, `FIRST_LOGIN`, `PASSWORD_CHANGED`, `PASSWORD_RESET_REQUESTED`, `PASSWORD_RESET_COMPLETED`, `LOGIN_FROM_NEW_DEVICE`, `TG_LINKED`, `TG_UNLINKED`, `GITHUB_LINKED`, `GITHUB_UNLINKED`, `PROFILE_CHANGED`, `ACCOUNT_DEACTIVATED`, `ACCOUNT_RESTORED`. Матрица соответствует плану в `docs/tasks/email-service.md:99-121`; пункты `EMAIL_CHANGE_*` исключены, поскольку самостоятельной смены email в продукте нет.
* `ipAddress` и `userAgent` начинают фиксироваться. Требуется провести `Request` (или минимально ip/ua) через сигнатуры затронутых методов `AuthService` и `UsersService` — это изменение сигнатур, а не косметика.
* Аудит пишется **в той же транзакции**, что и изменение, через outbox (ADR-003): security-событие недопустимо потерять.

### Первая авторизация

* В `User` добавляется `firstLoginAt DateTime?`, выставляемый в `loginUser` (`auth.service.ts:328`) — единой точке для всех способов входа.
* Приветственное уведомление отправляется **по факту первого веб-сеанса**, а не в момент OAuth-коллбэка: для GitHub/Telegram-пользователей `createdAt == firstLoginAt`, и приветствие, отправленное в момент регистрации, приходит в систему, где человек ещё не находится. Реализуется проверкой источника входа при вызове `loginUser`.

### Смена пароля

* Событие `PASSWORD_CHANGED` создаётся в той же транзакции, что и обновление хеша и инкремент `generation`.
* **In-app уведомление о смене пароля не отправляется в момент события** — оно было бы недостижимо (все сессии отозваны). Это осознанное решение, а не упущение. Компенсирующий показ при следующем входе — см. «Недоступность обоих каналов».
* Канал в текущем объёме: **только Telegram-пуш** (при наличии `telegramChatId`). Email-канал появляется вместе с транспортом из `docs/tasks/email-service.md`. Текст уведомления включает время, ip и user-agent.
* Отдельно фиксируется: `AuthRevocationTask` — не журнал событий. Строка удаляется после успешной отзыва (`auth.service.ts:563-567`), и таблица существует только на окне сбоя. Использовать её как аудит нельзя.

### Привязки каналов

* **Telegram-отвязка** переводится на подтверждение кодом. Новая одноразовая запись с TTL; бот показывает код владельцу чата; `unlink` выполняется только по предъявленному коду.
* Привязка Telegram становится событием безопасности, и `generation` при ней **инкрементируется с отзывом сессий**. Без этого уведомление «привязка отвязана, остальные сессии завершены» будет ложью: сессии сейчас не завершаются.
* `unlink` в текущем виде (`@Public()` + service key + `chatId` в теле) сохраняется как внутренний эндпоинт для бота. Веб-сценарий, если он нужен, реализуется **отдельным** user-facing эндпоинтом — не этим.
* **Добавляется отвязка GitHub** (`githubId → null`) с ревокацией сессий, событием `GITHUB_UNLINKED` и уведомлением. Порядок: сначала появляется сама возможность отвязки, затем уведомление о ней.
* `resetPassword` при `!telegramLinkVerified` обнуляет `telegramId`/`telegramUsername` (`:822`) — дополняется обнулением `githubId`, чтобы смена пароля разрывала и GitHub-доступ.
* Мёртвые поля `telegramId`, `telegramLinkVerified`, `telegramUsername` приводятся в соответствие: либо заполняются, либо удаляются. `telegramUsername` сейчас всегда `null` на стороне бота, хотя возвращается в DTO.

### Изменение профиля

* Событие `PROFILE_CHANGED` создаётся при обновлении профиля, **но не содержит значений полей**: сохраняются только имена изменённых полей. Иначе уведомление превращается в канал утечки и позволяет спамить самому себе.
* `telegramUsername` исключается из уведомлений до закрытия free-text вектора (см. «Последствия»: его либо убирают из `updateProfileSchema`, либо делают проверяемым через подтверждение во владении аккаунтом Telegram).

### Ретенция событий

* `SecurityEvent` **не удаляется каскадом** при soft-delete аккаунта (`User.deletedAt`) — удаление каскада действует только при окончательном затирании пользователя.
* Хранение — **12 месяцев** с момента создания события, затем очистка кроном.
* Окончательное затирание аккаунта (`user-cleanup.cron.ts`) удаляет события вместе с пользователем.
* Доступ к `ipAddress` и `userAgent` ограничен: эти поля не попадают ни в один публичный DTO и ни в экспортные выборки, включая административные.

### Порог срабатывания `LOGIN_FROM_NEW_DEVICE`

Основание — **нормализованный user-agent**, ip и user-agent записываются в событие всегда, но в решении об использовании не участвуют.

* Событие создаётся, если за последние **90 дней** не было ни одной успешной сессии с тем же нормализованным user-agent.
* Сравнение по ip **не применяется**: мобильный интернет и корпоративные NAT дают ложные срабатывания на каждом втором входе, что обесценивает уведомление целиком.
* В тексте уведомления ip и user-agent приводятся как контекст, а не как основание для вывода.

### Недоступность обоих каналов

Если у пользователя нет `telegramChatId` и отсутствует почтовый транспорт, security-событие остаётся только в `security_events` и **показывается как in-app уведомление при следующем входе** — как компенсирующий канал.

Обоснование: без этого события о смене пароля не будут увидены вовсе, что хуже, чем показ с задержкой. In-app-уведомление в этом сценарии доставляется не в момент события, а при следующей успешной авторизации, и это указывается в его тексте.

### Объём работ по email

**Почтовый транспорт в эту задачу не входит** и реализуется отдельно по `docs/tasks/email-service.md`.

В настоящей задаче security-события: записываются в `security_events`, отправляются в Telegram при наличии привязки, и при недоступности обоих каналов показываются in-app при следующем входе. Никаких заглушек, имитирующих email, не вводится; канал считается недоступным до появления реального транспорта.

### Объём по отвязке GitHub

Отвязка GitHub **входит в эту задачу**. Реализуется в следующем порядке:

1. Эндпоинт отвязки `githubId → null` с ревокацией сессий (инкремент `generation`).
2. Событие `GITHUB_UNLINKED` в `security_events` и в outbox.
3. Уведомление через доступные каналы.
4. Обнуление `githubId` в `resetPassword` (`:822`).

Без шага 1 шаги 2–3 не регистрируются: уведомлять об отвязке, которой нельзя совершить, нельзя.

## Последствия

* **Миграции БД:** `User.firstLoginAt`; таблица `security_events`; расширение `User` под ретенцию событий; outbox — по ADR-003.

### Порядок миграций: общая миграция `User`

Настоящий ADR добавляет в `User` колонку `firstLoginAt`, ADR-002 добавляет в ту же модель `timezone`. Обе колонки аддитивные, но применяются они **одной миграцией**.

Причина: две последовательные миграции на одну модель в конкурентных ветках приводят к конфликту при слиянии (Prisma не разрешает конфликт в `schema.prisma` автоматически) и к лишнему простою при каждом развёртывании.

Практические требования:

* `timezone` получает `NOT NULL DEFAULT 'Europe/Moscow'`, `firstLoginAt` остаётся `NULL`-able. Для существующих пользователей первый вход уже произошёл, поэтому дата не выдумывается и приветственное уведомление им не отправляется.
* Миграция выполняется **до** миграций, затрагивающих `showcase_cards` и `match_requests` (ADR-002), поскольку те переводят timestamp-колонки в `timestamptz(3)` и переписывают таблицы.
* Порядок и требования зафиксированы также в ADR-002, раздел «Порядок миграций».
* **`apps/api`:** фиксация ip/ua и запись `SecurityEvent` в затронутых сервисах; изменение сигнатур `AuthService`/`UsersService`; отвязка GitHub и подтверждаемая отвязка Telegram; инкремент `generation` при отвязках; чистка `githubId` в `resetPassword`.
* **Зависимость:** доставка по email **не входит в объём** настоящей задачи. До появления транспорта (`docs/tasks/email-service.md`) security-события отправляются в Telegram, а при недоступности обоих каналов показываются in-app при следующем входе. Заглушек, имитирующих email, не вводится.
* **`apps/telegram-bot`:** обработчик подтверждения отвязки по коду; новые типы сообщений.
* **`packages/i18n`:** тексты security-событий; отдельный namespace.
* **`apps/web`:** экран истории событий безопасности; UI подтверждения отвязки; предупреждение в настройках, если привязка Telegram снимается.
* **Вне объёма настоящей задачи, но фиксируется как обязательное:** `mail.service.ts` пишет сырой reset-токен в лог и формирует ссылки на `localhost:3000` в проде. Обе проблемы устраняются вместе с появлением реального транспорта.
* **Безопасность:** `SecurityEvent` содержит ip и user-agent. Эти поля не попадают ни в один публичный DTO и ни в экспортные выборки, включая административные; события очищаются по политике ретенции.

## Открытые вопросы

_Открытых вопросов нет._ Все пять ранее открытых решений приняты и перенесены в раздел «Принятое решение»: ретенция событий, порог `LOGIN_FROM_NEW_DEVICE`, поведение при недоступности обоих каналов, объём по отвязке GitHub, объём работ по email.
