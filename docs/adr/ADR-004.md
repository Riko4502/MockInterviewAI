# ADR-004: Транспорт доставки уведомлений (Redis Streams для SSE, RabbitMQ для Telegram)

## Статус
Принято

## Контекст и проблема

Требовалось «связать SSE с API» и «передать события через RabbitMQ». Проверка состояния репозитория показала, что обе предпосылки уже (частично) выполнены, но в неконсистентном состоянии.

### SSE и API уже связаны

Путь от `apps/api` до браузера работает end-to-end:

```text
apps/api  NotificationsService.createNotification
  → RedisService.xadd  (redis.service.ts:368)
    → ключ "user:{userId}:notifications", MAXLEN ~ 100, TTL 7 дней
      (notifications.service.ts:257-263, 290-292)
        → apps/realtime  RedisStore.ReadStream  (internal/storage/notifications.go:159)
          → SSE-кадр "notification.new" / "notification.badge"
            → apps/web  NotificationRealtime  (features/notification-realtime/ui/NotificationRealtime.tsx)
```

Не хватает не связи, а **продюсеров**: `createNotification` (`notifications.service.ts:172`) вызывается только из спецификаций. Отдельная задача «связать SSE с API» не требуется — она сводится к появлению продюсеров (ADR-003, ADR-005).

### RabbitMQ существует как инфраструктура, но не как код

* `docker-compose.yml:103-119` и `docker-compose.prod.yml:33-43` поднимают брокер.
* `.env.example:37-43` содержит `RABBITMQ_*`.
* `docker-compose.prod.yml:72` объявляет `RABBITMQ_URL=${RABBITMQ_URL:?RABBITMQ_URL is required}` — то есть **прод не стартует** без переменной.
* При этом `apps/api/src/config/configuration.ts` не содержит секции `rabbitmq`, а `apps/api/src/config/env.validation.ts` не валидирует ни один `RABBITMQ_*`. Переменная передаётся в контейнер, который её не читает.
* Клиентских библиотек нет: ни `amqplib`, ни `amqp-connection-manager`, ни `bullmq`, ни `nats` — ни в одном `package.json`.

### Контракт потока уже разъехался

Оба производителя пишут в **один и тот же** ключ `user:{userId}:notifications`, но разными наборами полей:

| Поле | `apps/api` (`redis.service.ts:375-385`) | `apps/realtime` (`notifications.go:110-121`) |
|---|---|---|
| `type` | да | да |
| `payload` | да | да |
| `timestamp` | **нет** | да (`:117`, RFC 3339) |

`convertMessages` (`notifications.go:343-354`) читает `timestamp` в `StreamEvent.Timestamp`; для событий, опубликованных `apps/api`, это поле окажется пустым. Дополнительно docstring `redis.service.ts:349-352` описывает поле как `data`, тогда как код пишет `payload`.

Другие расхождения:

* `apps/realtime/SSE_SPEC.md:151-160` обещает в `notification.new` поля `createdAt` и `read`; `createNotification` (`notifications.service.ts:191-197`) их не отправляет.
* Словарь типов событий существует в двух несвязанных местах: восемь констант в Go (`internal/sse/event.go:14-39`) и сырые строки в NestJS (`notifications.service.ts:191`, `:247`). Компилятором они не связаны. Из восьми типов продюсеров имеют только два.
* Два несвязанных словаря категорий: `NotificationType` в Prisma (`SYSTEM | INTERVIEW | MESSAGE`, `schema.prisma:135-139`) и `NotificationCategory` в Go (`info | success | warning | error`, `event.go:47-61`). Слово «category» означает разное в разных слоях, маппинга нет.
* Канал `matchmaking:events` (`matchmaking.service.ts:683-699`) публикует `match.accepted` без единого подписчика.

## Рассмотренные варианты

1. **Перевести всё на RabbitMQ.** Отклонено. SSE-путь уже работает и покрыт фронтендом; перенос создаёт два источника правды для одних и тех же данных с разной семантикой (Redis Stream — `MAXLEN ~ 100` + TTL 7 дней + at-least-once; RabbitMQ — acks, DLQ, ручной retry) без выигрыша.
2. **Оставить всё на Redis Streams, RabbitMQ не вводить.** Отклонено. `apps/telegram-bot` — отдельный сервис, которому нужны подтверждение доставки, повтор с backoff и DLQ (это прямо зафиксировано в `docs/TELEGRAM_BOT_ARCHITECTURE.md:36-39,82`). Redis Stream для этого не предназначен.
3. **Разделить по владельцам процесса: Redis Streams — только in-app/SSE, RabbitMQ — только Telegram.** Принято.

## Принятое решение

### Разделение транспортов

| Транспорт | Канал | Продюсер | Консьюмер | Семантика |
|---|---|---|---|---|
| Redis Stream `user:{userId}:notifications` | in-app события | `apps/api` | `apps/realtime` (Go) | best-effort, `MAXLEN ~ 100`, TTL 7 дней, replay по `Last-Event-ID` |
| Redis Pub/Sub `notifications:broadcast` | общесистемные оповещения | админ/CLI | `apps/realtime` | fire-and-forget |
| Redis Pub/Sub `auth:revocations` | отзыв авторизации | `apps/api` | `apps/realtime` | fire-and-forget |
| RabbitMQ `telegram.notifications` (+ DLQ) | push в Telegram | `apps/api` (продюсер, без консьюмера) | `apps/telegram-bot` | at-least-once, ack, retry с backoff, DLQ |
| outbox (таблица БД) | буфер между транзакцией и транспортом | `apps/api` | релей `@nestjs/schedule` | гарантия отсутствия потерь |

События **не дублируются** между транспортами: канал доставки выбирается один раз диспетчером (ADR-003), а не рассылается во все.

### Что связывается между API и SSE

Формально связывать нечего. Требуется устранить расхождения, найденные выше, **до** добавления новых типов событий — иначе они разъедутся так же:

* **Единый формат записи в стрим.** `timestamp` обязателен и пишется обоими производителями. `apps/api` добавляет его в `xadd`; docstring `redis.service.ts:349-352` приводится в соответствие (`payload`, а не `data`).
* **Единый словарь типов событий.** Имена и payload-схемы переносятся в `packages/types` / `packages/dto` с Zod-валидацией. `apps/api` генерирует из него Go-файл (`enum`/константы) на этапе сборки; `apps/realtime` импортирует. Исключение из ручного дублирования в двух языках закрыто.
* **Устраняется расхождение категорий.** Go `NotificationCategory` — визуальная severity для отрисовки, Prisma `NotificationType` — бизнес-домен. Словари переименовываются так, чтобы не совпадать: визуальная severity переезжает в поле `severity` payload'а, `NotificationType` остаётся единственным «category» в БД.
* **Payload приводится к `SSE_SPEC.md`.** `notification.new` начинает содержать `createdAt` и `read`; спецификация обновляется как источник правды.
* **Канал `matchmaking:events` поглощается.** Публикация `match.accepted` переводится на outbox → диспетчер → in-app + Telegram, а сам канал и его `publish` удаляются, поскольку единственный контракт — мёртвый.

### Подключение RabbitMQ

* В `apps/api` — **только продюсер** (`amqplib` + `amqp-connection-manager` для переподключения и подтверждений). Консьюмера в `apps/api` нет и не планируется.
* В `apps/telegram-bot` — **только консьюмер** очереди `telegram.notifications` с ack, retry и DLQ.
* `RABBITMQ_URL` добавляется в `configuration.ts` (секция `rabbitmq`) и в `env.validation.ts`. До этого `docker-compose.prod.yml:72` требует переменную, которую приложение не читает.
* Публикация выполняется **только из релея outbox**, а не из доменного кода: с точки зрения транзакции это одна операция.
* Потребитель обязан соблюдать rate limit Telegram Bot API (429) — это основной источник повторов и повод для DLQ.

### Идемпотентность

Оба транспорта — at-least-once. Дедупликация обеспечивается ключом `dedupKey` (ADR-003) и проверкой на стороне потребителя: Redis Stream дедуплицируется по `Last-Event-ID` и replay-окну, RabbitMQ — по `messageId` в заголовке.

### Недоступность брокера

Приложение **не падает** при недоступности RabbitMQ: HTTP-запросы продолжают обрабатываться, а публикация буферизуется в outbox до восстановления брокера. Релей при этом не накапливает бесконечный рост молча — фиксируются метрики и алерт.

Пороги алерта: возраст самой старой неотправленной строки outbox **более 5 минут** либо накоплено **более 1000** неотправленных строк. Превышение любого порога означает, что security-уведомления перестают доставляться в Telegram, и это требует реакции человека, а не ожидания.

События, для которых брокер обязателен, не помечаются как доставленные в момент записи в outbox — они считаются доставленными только после подтверждения брокера.

### Retry и DLQ

* Не более **5 попыток** доставки с экспоненциальной задержкой (1 с, 2 с, 4 с, 8 с, 16 с), затем сообщение уходит в `telegram.notifications.dlq`.
* Сообщения в DLQ хранятся **7 дней** и после удаляются кроном. Разбираются вручную оператором; автоматического «повторить позже» нет, чтобы недопустимые сообщения не циклились.
* Попадание в DLQ — событие для алерта, аналогично недоступности брокера. Типичные причины: `chatId` невалиден, пользователь заблокировал бота, превышен rate limit Telegram.
* Отправка `bot.ban`/`chat not found` и аналогичных невосстановимых ошибок **не повторяется** — сообщение сразу уходит в DLQ, чтобы не расходовать попытки на заведомо безнадёжный адресат.

### Источник правды по счётчику непрочитанных

Единственный источник правды — **поток событий**. Событие `notification.badge` является каноническим; расхождение между ним и значением в БД означает ошибку, а не штатное состояние.

Опросный `GET /notifications/unread-count` **сохраняется**, но его роль меняется: он используется только для первичной загрузки страницы при отсутствии живого SSE-соединения (или после полного обрыва потока с последующим восстановлением). Он не является источником истины и не должен использоваться для периодического опроса.

Кэш на 60 секунд (`notifications.service.ts:11`, `:102`) в пути опроса сохраняется как защита от частого переподключения, но поток принудительно сбрасывает его при публикации (`invalidateCache`, `notifications.service.ts:266-275`), поэтому расхождение ограничено во времени.

### Общесистемные оповещения

`system.broadcast` **не входит** в объём настоящей работы. Административного эндпоинта не будет: публикация остаётся через существующий CLI `scripts/send-sse.mjs`. Отсутствие эндпоинта отмечается как известный долг.

## Последствия

* **`apps/api`:** `timestamp` в `xadd`; продюсер RabbitMQ; релей outbox; `configuration.ts` + `env.validation.ts` для `RABBITMQ_*`; удаление `publishMatchAcceptedEvent`; генерация Go-констант событий.
* **`apps/realtime`:** импорт сгенерированных типов вместо ручных констант (`event.go:14-39`); переименование `NotificationCategory` → `severity` в payload'ах; обновление `SSE_SPEC.md`.

### Генерация типов событий для Go

Исключение ручного дублирования словаря событий между TypeScript и Go требует появления **кодогенерации между двумя языками** — в репозитории её нет. Механизм задаёт формат, но не место и не способ запуска.

Требования к решению:

* Единственный источник правды — `packages/types` (ADR-003). Сгенерированный Go-файл **коммитится** в `apps/realtime`, а не генерируется в рантайме: иначе сборка Go-сервиса перестаёт быть воспроизводимой без Node.
* CI обязан проверять, что сгенерированный файл совпадает с текущим содержимым `packages/types`. Иначе расхождение вернётся ровно в том виде, ради которого генерация вводится.
* Генератор обязан падать при расхождении схем, а не молча пропускать неизвестные поля.
* `go generate` либо аналогичная цель подключается в `apps/realtime`, генератор размещается в `packages/types` или в корне монорепозитория.

Механизм, место и способ запуска генератора вынесены в открытые вопросы — решение принимается при написании кода, поскольку оно влияет на CI и воспроизводимость сборки.
* **`apps/telegram-bot`:** консьюмер `telegram.notifications` с ack/retry/DLQ; переход на `type` + `payload` + `locale` (ADR-003).
* **Наблюдаемость:** метрики длины outbox, глубины очереди, числа повторов и попаданий в DLQ. Недоставленные сообщения, оставшиеся в DLQ, **не должны** теряться молча — требуется алерт.
* **DevOps:** в prod теперь действительно используется уже объявленный `RABBITMQ_URL`; необходимо описать процедуру перезапуска при недоступности брокера и поведение приложения (продолжать работу с отложенной публикацией из outbox, а не падать).
* **Пустое место, требующее проверки:** лимит 5 SSE-соединений на пользователя (`apps/realtime/SSE_SPEC.md:179-181`). Перед расширением числа типов событий требуется убедиться, что вкладка = соединение и обычный пользователь не упирается в `429`.

## Открытые вопросы

1. **Механизм кодогенерации TS → Go.** В репозитории нет генерации между языками. Требуется выбрать инструмент и определить, где живёт генератор: генератор внутри `apps/realtime` (проще, но изолирует знание о формате) либо в `packages/types` рядом с источником правды (правильнее, но добавляет в пакет ответственность за Go-вывод). Требования к решению зафиксированы в разделе «Генерация типов событий для Go»: файл коммитится, CI проверяет актуальность, генератор падает при расхождении схем. Влияет на CI и на воспроизводимость сборки Go-сервиса.

Остальные ранее открытые решения приняты и перенесены в раздел «Принятое решение»: поведение при недоступности брокера, retry и DLQ, источник правды по счётчику непрочитанных, объём по общесистемным оповещениям.
