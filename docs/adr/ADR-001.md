# ADR-001: Тикет-аутентификация WebSocket-подключений

## Статус
Принято

## Контекст и проблема
WebSocket-соединения к сервису `apps/realtime` открывались напрямую с access-токеном (из `HttpOnly` cookie или `Authorization: Bearer`), передаваемым на HTTP Upgrade handshake. Это создавало проблемы:

1. **Нет точечной ревокации access-токенов:** access-токены короткоживущие, но действительны до `exp`; при logout или смене пароля активные WS-соединения не прерывались мгновенно и могли продолжать получать события до истечения токена.
2. **Нет привязки к комнате:** сервер не мог гарантировать, что предъявленный токен соответствует именно той сессии интервью (`sessionId`), к которой открывается соединение.
3. **Распространение чувствительного токена:** access-токен в заголовках Upgrade увеличивает поверхность атаки (перехват, кэширование прокси) и усложняет безопасное переиспользование между вкладками.
4. **Нет контроля одноразовости:** одно и то же «удостоверение» могло использоваться для неограниченного числа параллельных соединений.

## Рассмотренные варианты
1. **Access-токен / cookie напрямую на handshake** (статус-кво): просто, но нет ревокации, нет привязки к комнате, нет контроля количества соединений. Долговечный refresh-токен на handshake недопустим по соображениям XSS/гигиены.
2. **Короткоживущий одноразовый тикет, выпускаемый API:** клиент получает тикет через аутентифицированный HTTP-запрос `POST /realtime/ticket` и передает его в `Sec-WebSocket-Protocol`. Тикет привязан к `sessionId`, одноразовый (по `jti`), `exp ≈ 5 мин`. Минус: дополнительный RTT перед каждым подключением и для каждого соединения.
3. **Тикет + мультиюз-фолбэк на `typ: "access"`:** во время раскатки допустить рукопожатия с обычным access-токеном (проверка только `blacklist:token:{jti}`), затем fail-closed переключить на тикеты.

## Принятое решение
Реализовать **тикет-аутентификацию WebSocket** (вариант 3, с промежуточным фолбэком на access):

* **`POST /realtime/ticket`** (глобальный префикс `/api/v1`), защищен `AccessTokenGuard` (live-проверка сессии), `AuthThrottlerGuard` (лимит по IP), `OriginCheckGuard` (точный матч Origin/Referer, допускается self-origin). Ответ: `{ ticket }`.
* **Тикет** — JWT HS256 на общем секрете `JWT_ACCESS_SECRET`: `typ: "realtime"`, `sid`, `sessionId`, `exp ≈ 5 мин`.
* Клиент передает тикет в **subprotocol `realtime.ticket`**; приоритет извлечения кредов в realtime: **subprotocol-тикет → `Authorization: Bearer` → cookie**.
* Верификация в realtime: `VerifyToken` (HS256, `typ ∈ {access, realtime}`, обязателен `sid`); для `typ == "realtime"` — одноразовый `ConsumeTicket(jti)` и привязка к комнате (`claims.SessionID == sessionId` из URL, иначе `403`); для `typ == "access"` — мультиюз `IsTokenRevoked` (обратная совместимость при раскатке).
* Live-валидация сессии: зеркало `auth:session:{sid}` (active/members) в Redis; realtime продлевает его TTL при входе участника.
* Ревокация: logout выставляет access в `blacklist:token:{jti}` и публикует в канал `auth:revocations`; realtime вызывает `Hub.EvictUser(userID)` и закрывает WS `StatusPolicyViolation`.
* Каждое новое соединение требует свежий тикет; после refresh access-токена (ротация `sid`) тикет выпускается заново.

## Последствия
* **Backend (`apps/api`):** глобальный async `AccessTokenGuard` (live Redis-проверка), `AuthThrottlerGuard` на тикет, `hset/hget/hdel` в `RedisService`, owner-only `POST /sessions/:id/participants|close`, ревокация access при logout.
* **Realtime (`apps/realtime`):** пакет `internal/auth` (JWT-верификация, `ConsumeTicket`, `IsTokenRevoked`), потенциальный разрыв рукопожатий без тикета при включении fail-closed — требуются согласованный деплой с API и фолбэк `typ: "access"`.
* **Frontend (`apps/web`):** двухшаговое подключение (тикет → WS с subprotocol), перевыпуск тикета после refresh и по `401`, reconnect с backoff, обработка кода закрытия `1008 StatusPolicyViolation`.
* **DevOps:** `JWT_ACCESS_SECRET` общий для `api` и `realtime`, в prod `ALLOWED_ORIGINS` realtime без `*`; Redis — hard-зависимость API (зеркала сессий) и новый e2e-тест тикетов требует Redis локально и в CI.
* Спецификация и план реализации: `apps/api/docs/spec-realtime-ws-auth.md`, `apps/api/docs/plan-realtime-ws-auth.md`.

## Изменения после реализации

Финальная реализация (Phase A/P12, `apps/api/docs/plan-realtime-ws-auth.md`) уточнила следующие формулировки:

* **Ревокация без записи в `blacklist:token:{jti}`:** отзыв выполняется удалением ключа `auth:session:{sid}` + публикацией в канал `auth:revocations` (`{instanceId, data: userId, sessionId?}`); realtime вызывает `EvictUser` (все комнаты) или `EvictFromRoom` (close-сессии).
* **Субпротокол на wire:** `Sec-WebSocket-Protocol: realtime, <ticket>` (клиент: `new WebSocket(url, ["realtime", ticket])`), согласованный subprotocol — `realtime`.
