# Дашборд: источники данных и устройство

Дашборд — составной блок интерфейса в слое widgets по FSD. Он экспортируется через @/widgets/dashboard, а маршрут App Router собирает его публичные компоненты.
Существующая entities/session отвечает за аутентификацию, а не за интервью. Для приветствия используется useCurrentUser из @/entities/user.
Во второй итерации серверный маршрут получил клиентские блоки Hero / Live Match и быстрые действия. Другие виджеты не должны импортировать этот виджет. Общую предметную логику следует до повторного использования перенести в подходящие entities или features.

Запросы используют существующие хуки Orval и URL-ключи из @packages/api; ключи списков учитывают необязательный лимит. Ответы сохраняются вместе с оболочкой, включая признаки пустого состояния. Типы модели выводятся из сгенерированных DTO без копирования полей. Ошибки транспорта доступны в запросах и мутациях и обрабатываются существующим HttpError. Все хуки работают внутри существующей границы аутентификации и провайдера QueryClient.

## Мутации и кеш

- Принять заявку: mutate({ id }); отклонить: mutate({ id, data: { reason? } }). Обе операции инвалидируют только ключи заявок дашборда, включая варианты с разными лимитами. При принятии сервер меняет статус и публикует событие, но не создаёт интервью, поэтому кеш ближайшей сессии не инвалидируется.
- Поднять анкету: mutate({ id }); инвалидируется только кеш статуса анкеты.
- Переключить Live Match: mutate({ data: { isSearching, specialization, level } }). Специализация и уровень обязательны и при остановке поиска: нужно передавать те же параметры очереди.
  Оптимистические состояния SEARCHING / IDLE очищают устаревшие данные сессии. При ошибке состояние откатывается, при успехе заменяется ответом сервера. MATCHED дополнительно инвалидирует кеш ближайшей сессии.
  Одновременные переключения из нескольких экземпляров хука отклоняются до отправки HTTP-запроса; во время мутации переключатель блокируется. Автоматических повторов нет, так как операция может создать сессию.
  useLiveMatchStateQuery наблюдает общий кеш без HTTP-запроса. Начальный null означает неизвестный статус. GET-эндпоинта статуса, опроса сервера, фиктивного подбора, сохранения состояния и интеграции через SSE нет.

## Ограничения контрактов

Все GET-контракты дашборда и контракт переключения Live Match существуют. Сгенерированные ответы принятия, отклонения и поднятия анкеты имеют тип void, хотя сервер возвращает объекты; в этой итерации тела намеренно не используются. Новые DTO и эндпоинты не добавляются. Подсчёт серии дней, процента готовности, возможности поднятия анкеты и правила подбора остаются ответственностью backend.
Ключи шагов готовности переводятся на клиенте; текст задачи дня и рекомендаций поступает с сервера. Синхронизацию в реальном времени и восстановление после перезагрузки нужно добавить отдельно.

Для форматирования дат и времени нужно явно задавать локаль и часовой пояс. Для некорректных дат возвращается пустая строка; некорректная или отрицательная длительность ограничивается нулём. Длительность не сбрасывается после 24 часов.

## Итерация 2: интерфейс

Серверный маршрут независимо собирает клиентские Hero и быстрые действия. Отступы уже задаёт боковая панель; остальные слоты виджетов пока пусты. Быстрые действия не ждут загрузки профиля или данных дашборда.
Hero использует существующий запрос профиля. Начальное приветствие безопасно для гидратации, а после монтирования переключается на местное время браузера: утро — 05–11, день — 12–17, вечер — в остальное время. В профиле нет targetSpecialization / targetLevel; типизированные необязательные свойства оставлены для будущей интеграции. Live Match предлагает явно выбрать параметры очереди, не угадывая их по профилю. Параметры очереди кешируются со статусом, чтобы поиск можно было остановить после возвращения на страницу. После перезагрузки они не сохраняются, неизвестный статус отображается явно. MATCHED приходит только от сервера и ведёт в существующую песочницу через ?room=sessionId. SSE и опрос не добавляются.
Быстрые действия используют существующую ссылку-якорь Live Match и маршруты песочницы. Страница поиска напарников пока не реализована. Лениво загружаемый диалог ИИ использует существующие примитивы Radix и позволяет выбрать черновые тему и сложность; запуск недоступен. Домена/API создания ИИ-интервью нет, обычное создание сессии не используется вместо него. Жёстко заданные подписи Dialog закрытия заменены явной переведённой кнопкой. Анимации радара учитывают настройку уменьшения движения.

## Итерация 3: готовность профиля

DashboardReadinessChecklist использует useReadinessChecklist — псевдоним существующего useReadinessQuery. Компонент отображает серверные totalPercentage и isCompleted без локального пересчёта. Состояния загрузки, ошибки, повтора и пустого списка следуют примеру виджета уведомлений: обычный useQuery, без Suspense для данных и общего ErrorBoundary. При 100% список сворачивается CSS-переходом сетки с поддержкой уменьшения движения.
Контракт содержит EMAIL_PROVIDED, а не EMAIL_CONFIRMED; API подтверждения почты отсутствует. Для привязки Telegram нужен подписанный payload Telegram Widget, но на фронтенде нет виджета или настроек QR/deep link. У backend есть эндпоинты создания анкеты, но в web-приложении нет страницы или формы. Эти действия отмечены недоступными: редактирование имени или переход на отсутствующую страницу не выдаются за завершение онбординга. FIRST_MOCK_COMPLETED ведёт в песочницу.
QuickMediaCheckDialog относится к существующей feature media-settings. Он проверяет камеру и микрофон независимо, использует локальные потоки и показывает видео. Для сохранения используются существующие мутация настроек устройств, ID клиента и функции получения названий устройств. Сохраняются только фактические названия дорожек; медиа не загружаются. После сохранения обновляется кеш устройств и через callback инвалидируется только готовность. Её результат определяет сервер. Дорожки останавливаются при закрытии, размонтировании и повторной проверке, в том числе потоки, пришедшие после отмены.

## Итерация 4: задача дня

DashboardDailyChallenge использует существующий сгенерированный запрос и URL-ключ DASHBOARD_KEYS.dailyChallenge. Ответ содержит длительность в секундах до сброса, рассчитанную backend до следующей полуночи UTC; временной метки сброса нет. Таймер отсчитывает длительность с момента получения ответа, обновляется раз в секунду и очищает интервал. При достижении нуля инвалидируется только точный ключ задачи дня для повторного запроса.
Виджет отображает серверные pointsReward и isSolvedToday. После решения скрывает действие получения награды в песочнице; клиент не реализует XP, серии дней или логику решения. Сложность отображается существующими семантическими метками статуса. Показываются максимум три тега и счётчик остальных. В песочницу передаётся фактический problemId.

## Итерация 5: ближайшая сессия

DashboardUpcomingSession использует сгенерированный запрос ближайшей сессии. Backend передаёт isReadyToJoin и secondsUntilStart; подключение разрешает только серверный признак готовности. При нуле обновляется точный ключ ближайшей сессии. Подключение использует существующий сценарий песочницы с ?room={session.id}. Пустое состояние позволяет создать комнату в песочнице или перейти к Live Match; отдельного маршрута поиска напарников нет.
Ответ содержит отображаемое имя, имя пользователя, URL аватара, специализацию и уровень напарника, но не его стек технологий. Карточка показывает только доступные поля. QuickMediaCheckDialog лениво загружается из media-settings. Таймер отсчитывает длительность API с момента получения, обновляется раз в секунду и очищает интервал по истечении или размонтировании.

## Итерация 6: виджеты поиска напарников

Для заявок используются сгенерированный запрос дашборда и мутации принятия/отклонения. Ожидающие обработки ID оптимистически скрываются; для каждого действует синхронная блокировка. Остальные заявки остаются доступными. Весь снимок кеша не заменяется: при ошибке снимается оптимистический слой и возвращается исходная заявка.
Успешная мутация удаляет только свою заявку из вариантов кеша списка и ожидает адресного повторного запроса. Ближайшая сессия не инвалидируется: принятие меняет статус и открывает контактные данные, но не создаёт интервью.
В API нет предпочтительного времени, поэтому createdAt не используется вместо него. Интерфейс сообщает, что время не указано, и сохраняет сообщение отправителя. Для анкеты используются серверные daysLeft и canBump; клиент не вычисляет задержку до следующего поднятия. После поднятия обновляется только кеш витрины, сообщение показывает существующий UI toast provider. Каждый виджет сам обрабатывает загрузку, пустые данные и повтор запроса.
Ограничение backend: viewsCount дашборда пока всегда равно 24; виджет отображает поле API и не считает свою статистику.

## Итоговая компоновка и аналитика

Серверный маршрут собирает DashboardFrame: одна колонка при ширине меньше lg и соотношение 8/4 при большей. Боковая панель уже задаёт p-6, поэтому повторный внешний отступ не добавляется.
Основная колонка: готовность, ближайшая сессия, задача дня, четыре карточки показателей, рекомендации и последние сессии. Дополнительная: входящие заявки, анкета и существующая проверка устройств. Hero / Live Match и быстрые действия стоят над колонками.
Статистика показывает общее число и число завершённых интервью, серверный currentStreakDays, необязательную среднюю оценку по десятибалльной шкале и общее число задач с разбивкой на лёгкие, средние и сложные. StatMetricCard и DashboardStatsLayout общие для карточек данных и скелетонов.
В рекомендациях показывается только API-контент; practiceUrl ограничивается существующей песочницей с контекстом topic/problemId. Запрос последних сессий передаёт limit=5; интерфейс использует completedAt, название, роль и необязательную оценку, не выдумывая маршрут отчёта. Сначала даты форматируются в UTC для безопасной гидратации, затем используется часовой пояс браузера.
Все сетевые виджеты используют обычные сгенерированные useQuery. Общий QueryClient настроен на retry=1, staleTime=5 минут, без повтора при фокусе и без throwOnError. Предзагрузки/гидратации серверных данных и useSuspenseQuery нет. Suspense загружает только код диалога после действия пользователя. Маршрутный loading.tsx показывает скелетон с раскладкой колонок; виджеты отдельно обрабатывают ожидание, пустые данные и ошибки. Маршрутный error.tsx позволяет повторить попытку при непредвиденной ошибке страницы, не раскрывая её подробности.
Скелетоны четырёх показателей повторяют итоговую раскладку и минимальные размеры карточек. Другие скелетоны лишь приблизительно соответствуют содержимому; фиксированные чрезмерные высоты и отсутствие CLS для контента любой длины не гарантируются.
QuickMediaCheckWidget не запрашивает камеру/микрофон, пока пользователь не откроет лениво загружаемый диалог. Настройки остаются в существующем кеше, инвалидируется только готовность. Новые HTTP-транспорт, провайдер запросов или DTO не добавляются.

Создание анкеты доступно в пустом состоянии «Моя анкета»: feature create-showcase валидирует поля общей DTO-схемой, публикует через useShowcaseControllerCreate и обновляет кеш статуса, готовности и витрины. Ошибки сохраняют введённые данные, повторная отправка во время публикации блокируется.

### Оставшиеся пробелы интеграции (проверены по исходному коду)

- Средняя оценка backend всегда null, solvedTasks пока равен нулю.
- Рекомендации AI сейчас статические и не являются персональным анализом.
- Последние сессии получают сгенерированное название, пустую оценку и hasFeedbackReport=false; нет темы, URL отчёта или web-маршрута отчёта/стенограммы.
- Песочница поддерживает комнату/приглашение, но пока не использует problemId/topic. Дашборд сохраняет контекст в ссылке; загрузку задачи нужно интегрировать в песочницу.
- У Live Match нет GET-статуса и SSE-синхронизации; после обновления страницы статус неизвестен.
- Создание ИИ-интервью, подтверждение почты и интерфейс привязки Telegram недоступны.
- Предпочтительное время заявки отсутствует; число просмотров анкеты задано на backend.

### Проверки

Vitest покрывает сценарии предыдущих итераций, значения показателей и обработку null/нуля, контекст рекомендаций и небезопасные ссылки, последние сессии, независимые ошибки и повторы, запасной интерфейс страницы и область обновления кеша после проверки устройств.
Playwright dashboard.spec.ts использует явные фикстуры API для ширины 375/768/1280/1920 пикселей в светлой/тёмной темах, длинного содержимого, навигации, соотношения колонок, переполнения, независимости от медленных запросов и стабильности высоты скелетона показателей.
Фикстуры проверяют контракт фронтенда, но не достоверность данных backend.
