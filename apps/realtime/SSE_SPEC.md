# Архитектурная спецификация: Сервис real-time уведомлений на базе Server-Sent Events (SSE)

Настоящий документ представляет собой детальное системное руководство и архитектурную спецификацию подсистемы **Server-Sent Events (SSE)** в сервисе `apps/realtime`. Документ фокусируется на архитектурных решениях, модели горизонтального масштабирования, гарантиях доставки, обработке граничных случаев и интеграции с инфраструктурой платформы.

---

## 1. Концепция и разграничение ответственности

В платформе  сетевые real-time протоколы разделены по типам задач:

```
                                  +-------------------------------------------------------+
                                  |                     Клиент (Web/App)                  |
                                  +---------------------------+---------------------------+
                                                              |
                               +------------------------------+------------------------------+
                               |                                                             |
                 (Сессионный трафик: 1 комната)                             (Глобальный аккаунт: весь сайт)
                               v                                                             v
            +------------------------------------+                        +------------------------------------+
            |        WebSocket Protocol          |                        |         SSE Protocol               |
            |     /ws/sessions/:sessionId        |                        |         /sse/notifications         |
            +-----------------+------------------+                        +-----------------+------------------+
                              |                                                             |
            +-----------------v------------------+                        +-----------------v------------------+
            |  - Двунаправленный обмен (Bi-dir)  |                        |  - Однонаправленный поток (S ➔ C)  |
            |  - Monaco Code editor sync         |                        |  - Персональные уведомления        |
            |  - Позиции курсоров и выделение    |                        |  - Инвайты на собеседования        |
            |  - WebRTC сигналинг (LiveKit)      |                        |  - Статусы автотестов (runner)     |
            |  - Текстовый чат сессии            |                        |  - Готовность AI-отчетов           |
            |  - Жизненный цикл = длительность   |                        |  - Жизненный цикл = сессия логина  |
            |    одного интервью (~60 мин)       |                        |    пользователя                    |
            +------------------------------------+                        +------------------------------------+
```

### Преимущества выбора SSE для уведомлений:
1. **Простота и надежность транспортного уровня:** Работа поверх стандартного HTTP(S) без необходимости протокольного рукопожатия `101 Switching Protocols`.
2. **Эффективность мультиплексирования HTTP/2:** Десятки SSE-потоков и API-запросов утилизируют единственное TCP/TLS соединение между клиентом и балансировщиком.
3. **Нативная поддержка протокола в браузерах:** Встроенный парсер W3C `EventSource`, автоматическое восстановление связи с экспоненциальным backoff и передача заголовка `Last-Event-ID`.

## 2. Архитектура данных и модель масштабирования

### 2.1. Распределенная топология (Multi-Instance Clustering)

Сервис `apps/realtime` проектируется как **stateless-кластер**, горизонтально масштабируемый за счет общего уровня персистентности и обмена сообщениями в **Redis**.

```
+---------------------------------------------------------------------------------------------------------+
|                                           Балансировщик нагрузки (Nginx / AWS ALB)                     |
|                                       - Балансировка: Round Robin / Least Connections                   |
|                                       - Протокол: HTTP/2 Termination                                    |
+-------------------+-----------------------------------+-----------------------------------+-------------+
                    |                                   |                                   |
                    v                                   v                                   v
    +-------------------------------+   +-------------------------------+   +-------------------------------+
    |  Realtime Node 1              |   |  Realtime Node 2              |   |  Realtime Node N              |
    |  - SSE Hub (UserSession map)  |   |  - SSE Hub (UserSession map)  |   |  - SSE Hub (UserSession map)  |
    |  - Вкладка 1 юзера A          |   |  - Вкладка 2 юзера A          |   |  - Вкладки юзера B, C         |
    +---------------+---------------+   +---------------+---------------+   +---------------+---------------+
                    |                                   |                                   |
                    +-----------------------------------+-----------------------------------+
                                                        |
                                                        v
+---------------------------------------------------------------------------------------------------------+
|                                    Слой данных (Redis Cluster / Sentinel)                               |
|                                                                                                         |
|   1. Redis Streams: "user:{userId}:notifications" (Хранение истории последних N событий пользователя)   |
|   2. Redis Pub/Sub: "notifications:broadcast"     (Мгновенная доставка общесистемных алертов)           |
|   3. Redis Pub/Sub: "auth:revocations"            (Мгновенный сброс авторизации на всех нодах)          |
|   4. Redis Keys:    "user:{userId}:sse_count"     (Счетчик активных соединений для Rate Limiting)       |
+---------------------------------------------------------------------------------------------------------+
```

### 2.2. Стратегия шардирования и управления потоками (Redis Streams)

* **Изолированный стрим на пользователя:** Использование ключей вида `user:{userId}:notifications`.
* **Ограничение глубины (Capped Streams):** Для предотвращения бесконечного роста памяти Redis публикация выполняется с модификатором приближенного ограничения:
  $$\text{XADD user:\{userId\}:notifications MAXLEN } \sim 100 \text{ * ...}$$
* **Установка TTL на стримы:** После публикации ключу стрима продлевается `EXPIRE` на 7 суток. Неактивные пользователи автоматически выгружаются из оперативной памяти Redis.
* **Долгосрочная персистентность (Persistent Storage):** Redis Streams используется исключительно как **буфер оперативной доставки (Transport Buffer)**. Полноценная история уведомлений (для открытия шторки «Все уведомления») сохраняется сервисом `apps/api` в PostgreSQL.

## 3. Гарантии доставки и жизненный цикл соединения

### 3.1. Модель семантики доставки (At-Least-Once Delivery)

```
[ Клиент ]                                         [ apps/realtime ]                          [ Redis Streams ]
    |                                                      |                                          |
    |--- GET /sse/notifications -------------------------->|                                          |
    |    (Last-Event-ID: 1724500000000-0)                  |                                          |
    |                                                      |--- XREAD user:123:notifications -------->|
    |                                                      |    (от ID > 1724500000000-0)             |
    |                                                      |<-- [Пропущенные события msg_1, msg_2] ---|
    |                                                      |                                          |
    |<-- event: notification.new (msg_1) ------------------|                                          |
    |<-- event: notification.new (msg_2) ------------------|                                          |
    |                                                      |                                          |
    |    (Переход в режим ожидания новых событий)          |--- XREAD BLOCK 15000 ------------------->|
    |                                                      |    (Ожидание новых XADD в стрим)         |
```

1. **Первичное подключение:** Клиент передает `Last-Event-ID` (если он ранее получал события).
2. **Фаза Replay (Восстановление):** Сервер запрашивает из Redis Stream события с ID больше полученного, компенсируя время, пока клиент был оффлайн (например, переключение между Wi-Fi и LTE).
3. **Фаза Live Streaming:** Сервер переходит в блокирующее чтение новых событий (`XREAD BLOCK`).
4. **Дедупликация на клиенте:** Каждое сообщение содержит детерминированный `id` (Redis Stream ID). Клиентский стейт-менеджер отфильтровывает дубликаты по `id`.

---

### 3.2. Многовкладочность (Multi-Tab Connection Multiplexing)

Пользователь может одновременно открыть несколько вкладок приложения:

1. **В рамках одного инстанса Realtime:**
   * Внутренний реестр `UserSession` хранит список всех активных соединений (`clients: map[clientId]*Client`).
   * Для одного `userId` запускается **ровно одна горутина вычитки** из Redis Stream.
   * Полученное событие мультиплексируется во все локальные вкладки через неблокирующие каналы.
2. **На разных инстансах Realtime (при балансировке без Sticky Sessions):**
   * Каждый инстанс с активной вкладкой пользователя читает один и тот же стрим `user:{userId}:notifications`.
   * Так как `XREAD` не удаляет сообщения из стрима, каждый инстанс независимо доставляет событие в свои локальные вкладки.

---

### 3.3. Защита от медленных клиентов (Slow Consumer Strategy)

* **Проблема:** Медленное сетевое соединение клиента (высокий RTT, буферизация на мобильном операторе) может заблокировать горутину отправки сервера.
* **Решение:**
  * Каждому соединению выделяется кольцевой буфер ограниченной емкости (например, 128 событий).
  * Запись в канал клиента выполняется через неблокирующий `select` с веткой `default`.
  * При переполнении буфера событие сбрасывается с инкрементом метрики `realtime_sse_dropped_messages_total`.
  * Если буфер остается заполненным в течение $N$ секунд, сервер принудительно закрывает соединение с кодом `408 Request Timeout`, вынуждая клиент переподключиться и запросить пропущенные данные через `Last-Event-ID`.

## 4. Спецификация контрактов и Wire Protocol

### 4.1. Канонический формат Wire-пакетов

Каждый фрейм SSE формируется строго по стандарту W3C:

$$\text{event: } \langle \text{EventType} \rangle \backslash\text{n}$$
$$\text{id: } \langle \text{RedisStreamID} \rangle \backslash\text{n}$$
$$\text{retry: } 3000 \backslash\text{n}$$
$$\text{data: } \langle \text{JSON Payload} \rangle \backslash\text{n}\backslash\text{n}$$

### 4.2. Справочник типов событий

| Event Type | Описание события | Инициатор (Producer) | Payload DTO |
| :--- | :--- | :--- | :--- |
| `notification.new` | Новое персональное уведомление | `apps/api` | `id`, `category`, `title`, `message`, `actionUrl`, `createdAt`, `read` |
| `notification.badge` | Обновление счетчика непрочитанных | `apps/api` | `unreadCount` |
| `session.invited` | Инвайт на интервью | `apps/api` | `sessionId`, `sessionTitle`, `inviterName`, `role`, `joinUrl`, `expiresAt` |
| `code_runner.status`| Статус выполнения тестов | `apps/code-runner` | `taskId`, `sessionId`, `status`, `passedCount`, `totalCount`, `timeMs` |
| `ai.report_ready` | Готовность аналитики интервью | AI Worker | `sessionId`, `reportId`, `score`, `summary`, `reportUrl` |
| `account.updated` | Смена баланса кредитов / тарифа | `apps/api` | `remainingCredits`, `plan`, `reason` |
| `system.broadcast` | Общесистемный алерт / техработы | Admin / Ops | `severity` (`info`/`warn`/`crit`), `message`, `maintenanceWindow` |
| `ping` | Heartbeat проверки живости канала | `apps/realtime` | Пустой комментарий `: ping <timestamp>\n\n` каждые 15 сек |

## 5. Безопасность и управление доступом

### 5.1. Аутентификация и защита от CSRF
1. **Заголовок `Authorization: Bearer <JWT>` — основной способ.** `apps/api` возвращает access-токен в теле ответа (`/auth/login`, `/auth/register`, `/auth/refresh`) и хранит в cookie только `refresh_token`, поэтому браузерный клиент открывает поток через `@microsoft/fetch-event-source` с заголовком `Authorization`; нативный `EventSource` заголовки выставлять не умеет и здесь неприменим.
2. **Чтение токена из Cookie — поддерживается, но API ее не выставляет.** Хендлер читает `HttpOnly`, `Secure`, `SameSite=Lax` Cookie с именем `JWT_ACCESS_COOKIE_NAME` (по умолчанию `access_token`), если она появится; тогда клиенту достаточно `credentials: "include"`. Приоритет у заголовка `Authorization`.
3. **Запрет токенов в GET Query String:** Передача `?token=...` запрещена, чтобы исключить утечку JWT в access-логи балансировщиков, историю браузера и заголовок `Referer`.
4. **Проверка живой auth-сессии (fail-closed).** Токен обязан нести `typ` (`access`/`realtime`) и непустой `sid`, а ключ `auth:session:{sid}` — существовать в Redis, иначе соединение отклоняется кодом `401`. Logout, выход со всех устройств, смена пароля и деактивация удаляют этот ключ, тогда как сам access-токен остается подписанным до `exp` (до 15 минут): без проверки клиент, разорванный по `auth:revocations`, немедленно переоткрыл бы поток тем же токеном. Проверка симметрична WebSocket-хендлеру; при `REDIS_ENABLED=false` поток недоступен.

### 5.2. Мгновенный отзыв авторизации (Token Revocation)
* При смене пароля, блокировке пользователя или выходе со всех устройств сервис авторизации публикует в канал Redis `auth:revocations` сообщение `{"instanceId":"api-<hostname>","data":"<userId>"}`.
* Все ноды `apps/realtime` слушают этот канал: при получении события все активные SSE-соединения пользователя немедленно разрываются с отправкой финального события `event: auth.revoked` и закрытием HTTP-стрима.
* Необязательное поле `sessionId` означает room-scoped ревокацию (закрытие конкретной комнаты интервью) и адресовано WebSocket-хабу: глобальный поток уведомлений к комнате не привязан, поэтому такие сообщения его не рвут — иначе выход из одного интервью гасил бы пользователю все уведомления.
* Разрыв потока не отменяет проверку на входе: переподключение с тем же (еще не истекшим) access-токеном отклоняется по отсутствию `auth:session:{sid}` — см. п. 4 раздела 5.1.

### 5.3. Защита от исчерпания ресурсов (Connection Limits)
* Ограничение: не более **5 одновременных SSE-соединений на одного пользователя** (`userId`).
* Ограничение: не более **20 соединений с одного IP-адреса**.
* Превышение лимита возвращает HTTP `429 Too Many Requests`.

## 6. Расчет нагрузки и оптимизация ресурсов (High Load & Scaling)

### 6.1. Расчет памяти на 100 000 активных онлайн-пользователей

В Go каждое HTTP SSE соединение удерживает открытую горутину и сокет:

| Компонент | Память на 1 соединение | Суммарно на 100k соединений |
| :--- | :--- | :--- |
| Go Goroutine Stack | ~4–8 KB | ~400–800 MB |
| Read/Write TCP Buffers | ~4–16 KB (с `tcp_rmem`/`tcp_wmem` тюнингом) | ~400 MB–1.6 GB |
| Буфер канала сообщений (128 указателей) | ~1 KB | ~100 MB |
| **Итого:** | **~10–25 KB** | **~1.0–2.5 GB RAM** |

*Вывод:* Один инстанс сервиса на Go с 4 ГБ RAM и 2 vCPU способен комфортно обслуживать **до 50 000 – 100 000 одновременных SSE-соединений** при правильной настройке ядра ОС.

### 6.2. Тюнинг сетевого стека ОС Linux (Sysctl)
Для работы высоконагруженного SSE-кластера на серверах настраиваются параметры ядра:
```ini
# Максимальное количество открытых файловых дескрипторов
fs.file-max = 2097152

# Размер очереди входящих соединений
net.core.somaxconn = 65535
net.ipv4.tcp_max_syn_backlog = 65535

# Оптимизация памяти TCP буферов под стриминг небольших сообщений
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216

# Повторное использование сокетов в состоянии TIME_WAIT
net.ipv4.tcp_tw_reuse = 1
```

## 7. Конфигурация Nginx и Edge-инфраструктуры

Для обеспечения стабильной работы долгоживущих потоков на уровне обратного прокси необходимо настроить:

1. **Протокол HTTP/2:** Предотвращает исчерпание лимита соединений в браузерах.
2. **Отключение буферизации (`proxy_buffering off`):** Обеспечивает мгновенную передачу чанков клиенту без накопления пакетов в буфере прокси.
3. **Отключение сжатия gzip для SSE:** Сжатие потока может задерживать отправку коротких сообщений.
4. **Увеличение таймаутов простоя (`proxy_read_timeout 3600s`):** Защищает от разрыва соединений при временном отсутствии событий.
